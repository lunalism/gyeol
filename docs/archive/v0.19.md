## 0. 이 문서의 목적

기능을 정의하기 위한 문서가 **아니다.** 기능을 거절하기 위한 문서다.

1인 개발 프로젝트의 사망 원인 1위는 기능 부족이 아니라 범위 팽창이다. 앞으로 "이것만 더 있으면"이라는 생각이 들 때 §6을 읽고, 거기 있으면 안 한다. §6에 없는 새 아이디어면 §6에 추가한다. 삭제는 v1 출시 이후에만 가능하다.

**이 문서가 지켜야 할 단 하나의 숫자: v1 출시까지 §5의 항목 수는 늘지 않는다.**

> **이 파일이 PRD의 유일한 정본이다.** v0.9와 리포지토리의 v0.8 수정분이 갈라졌던 것을 여기서 병합했다. 앞으로 개정은 이 파일에만 한다.

## 2. 왜 만드나

현재 맥에서 영상을 자르고 자막을 붙이려는 사람의 선택지:

||문제|
|---|---|
|CapCut|무료 기능이 계속 유료로 전환됨. 클라우드 업로드 전제. 중국 기업 의존.|
|Final Cut Pro|40만원. 자동 자막이 약하고 한국어는 특히. 컷 편집만 하기엔 과함.|
|Premiere Pro|구독. 맥에서 무겁고 이질적.|
|Kdenlive / Shotcut / OpenShot|전부 Qt 기반 크로스플랫폼. 맥에서 이물감, 코덱 커버리지, GPU 가속 모두 열세.|
|DaVinci Resolve|훌륭하지만 컷 편집만 하려는 사람에겐 학습 곡선이 벽. 오픈소스 아님.|

**빈 자리:** 맥 네이티브 + 자동 자막 + 로컬 전용 + 오픈소스. 네 개를 동시에 만족하는 게 없다.

이건 "더 좋은 편집기"를 만드는 프로젝트가 아니라, **없는 조합**을 만드는 프로젝트다. 기능 경쟁으로 이기려는 순간 진다.

## 3. 타겟 사용자 — v1은 딱 한 명만 본다

**1인 영상 제작자.**

- **5분~3시간짜리 영상을 만든다**
    - 상한을 3시간으로 잡는 근거는 "긴 원본도 컷 편집은 되어야 한다"이다. 강연·팟캐스트·게임 실황·브이로그 원본이 여기 해당하며, 이들은 v1 기능만으로 실제 작업이 가능하다.
    - **음악 플레이리스트 영상 제작자도 v1 타겟이다.** 근거는 §4 S0 — 개발자 본인이 이 유형을 만들며, 오디오 스펙트럼 없이는 기존 유료 도구를 대체할 수 없다. 대체하지 못하면 dogfooding이 일어나지 않고, dogfooding 없는 1인 오픈소스는 유지되지 않는다. 이 판단으로 §5.8이 v1에 편입되었다.
    - 길이 상한이 3배 이상 늘어나면서 §4 S7과 §5.2 가상화 요구사항이 파생된다. 공짜가 아니다.
- 작업 시간의 90%가 컷 편집과 자막이다
- Final Cut을 살 만큼은 아니고, CapCut은 찝찝하다
- 색보정, 모션 그래픽은 필요하면 다른 도구를 쓴다

**언어는 한정하지 않는다.** 이 사람이 무슨 언어로 말하는 영상을 만들지 우리는 모른다. §5.4 참조.

다만 **개발자가 품질을 직접 평가할 수 있는 언어는 한국어와 영어뿐**이므로, "지원"과 "품질 보증"을 분리한다. 이건 범위를 좁히는 것이 아니라 검증 가능한 주장만 하는 것이다.

**명시적으로 타겟이 **아닌** 사람:**

방송국·제작사 워크플로, 컬러리스트, 모션 그래픽 디자이너, 다중 카메라 촬영자, 팀 협업 사용자.

이들의 요구를 받기 시작하면 v1이 안 나온다. 정중히 거절하고 로드맵에 적어둔다.

### 4.1 S3 검증 방법

**인코딩된 파일과 프리뷰 화면을 픽셀 비교하는 방식은 쓰지 않는다.** 내보내기는 손실 압축(H.264)과 색공간 변환(RGB→YUV 4:2:0)을 거치므로 프리뷰 버퍼와 비트 단위로 일치할 수 없다. 그런 테스트는 필연적으로 유사도 임계값을 도입하게 되고, 임계값이 들어가는 순간 정작 잡으려던 한 프레임 어긋남을 놓친다.

또한 **S3가 실제로 잡으려는 버그는 픽셀이 아니라 프레임 인덱스다.** 프리뷰는 디스플레이 리프레시 시점에, 내보내기는 프레임 경계에서 프레임을 요청한다. 시간 반올림이 미세하게 다르면 같은 시각에 서로 다른 프레임을 집는다. 29.97fps에서 발생하는 그 버그이며, 픽셀 비교로는 원인을 특정할 수 없다.

|층|대상|방법|잡는 것|
|---|---|---|---|
|**L1**|시간→프레임 매핑|동일 시각에 대해 프리뷰 경로와 내보내기 경로가 같은 프레임 인덱스를 산출하는지 비교. 모든 지원 프레임레이트(23.976 / 24 / 25 / 29.97 / 30 / 50 / 59.94 / 60)에 대해 수행|**시간 반올림 버그. 가장 중요한 층.**|
|**L2**|컴포지터 출력|`render(document, time)`이 반환한 `CVPixelBuffer`를 **인코딩 전에** 해시 비교. 프리뷰 설정과 내보내기 설정 양쪽 경로로 호출|렌더 경로의 상태 오염. 비트 단위 일치가 정상이므로 임계값이 필요 없다|
|**L3**|최종 산출물|내보낸 파일의 총 프레임 수, 길이, 첫/마지막 프레임 위치|파이프라인 레벨 실수(프레임 밀림, 길이 어긋남). **픽셀 정확도는 검사하지 않는다**|

**L2의 "버퍼를 해시한다"는 그대로 성립하지 않았다. M1.4에서 두 정밀화를 거쳤고, 둘 다 임계값을 도입하지 않는 방향이다.**

L2는 M1.4 이전까지 소비자가 없던 계약이었고, §9가 예고한 대로 실제 픽셀 버퍼와 만나자 구멍이 드러났다. 원칙 8·§5.6.8과 같은 경로다.

1. **픽셀 포맷을 컴포지터 양측에서 고정한다(420v).** 프리뷰 설정과 내보내기 설정의 기본 픽셀 포맷이 서로 다르다. 고정하지 않으면 같은 내용이 다른 바이트가 되고, 그 차이를 "허용 오차"로 흡수하려는 압력이 생긴다. 그것이 이 표가 거부하는 바로 그 임계값이다.
2. **해시는 이미지 바이트만 대상으로 한다.** `bytesPerRow` 패딩이 설정마다 달라 버퍼 전체를 해시하면 **정렬 차이로 오탐이 난다.** 정렬은 내용이 아니므로, 행별 유효 바이트만 해싱한다.

**핵심은 임계값을 넣지 않았다는 것이다.** 패딩과 포맷 차이는 내용의 차이가 아니라 표현의 차이이므로, 표현을 정규화해 비교하면 비트 단위 일치가 여전히 정답으로 남는다. M1.4에서 360프레임 전부 비트 동일을 확인했다(부록 A-32).

**API 이행 시 재검증 대상이며, 이행 대상이 둘로 갈린다**(v0.19, 부록 A-35).

1. **`AVMutableVideoComposition` 계열** — macOS 26.0에서 deprecated가 확정되었으나 **대체 타입이 26.5 SDK에 존재하지 않는다.** 이행 시점이 우리 손에 없다.
2. **컴포지팅 메서드의 픽셀 버퍼 타입** — `newPixelBuffer()` → `newReadOnlyPixelBuffer()`, `sourceFrame(byTrackID:)` → `sourceReadOnlyPixelBuffer(byTrackID:)`, `finish(withComposedVideoFrame:)`가 `CVReadOnlyPixelBuffer`를 받는 형태로. **대체 이름이 전부 명시되어 있어 이행 경로가 분명하다.**

**둘째가 L2에 직접 걸린다.** 현재 L2는 `CVPixelBuffer`의 이미지 바이트를 행별로 해싱하는데, **읽기 전용 버퍼의 잠금과 베이스 주소 접근 방식이 다를 수 있어 해싱 구현부터 손봐야 할 가능성이 있다.** 통과 조건은 그대로 "이행 후에도 360프레임 비트 동일"이다.

`AVMutableVideoComposition`이 macOS 26에서 deprecated이며 `AVVideoComposition.Configuration`으로 이행해야 한다(부록 A-32). 현재 L2는 프리뷰와 내보내기가 같은 컴포지터를 공유함을 전제로 비트 동일을 확인했는데, **이행 후에도 두 경로가 같은 컴포지터를 공유하는지는 보장되지 않는다.** L2가 이행 후에도 초록불인 것이 API 이행의 통과 조건이다.

**L3의 길이 비교 대상은 문서 `duration`이 아니라 `frameCount × ticksPerFrame`이다.**

`frameCount`는 ceil이므로 문서 길이가 프레임 경계에 맞지 않으면 내보낸 파일이 최대 한 프레임 길다. 문서 `duration`과 직접 비교하는 테스트는 **정상 동작에서 실패한다.** 이 사실을 모른 채 테스트가 빨개지면 원인을 찾지 못하고 허용 오차를 도입하게 되고, 그 순간 L3가 잡으려던 프레임 밀림을 함께 놓친다.

**L3는 컨테이너 타임스케일도 검사한다. 이것이 없으면 세 층 모두가 놓치는 경로가 남는다.**

M1 실측에서 확인된 것(부록 A-23): `AVAssetWriter`는 타임스케일을 지정하지 않으면 트랙을 QuickTime 기본값 600으로 양자화한다. 23.976으로 써넣은 정확한 PTS가 25/600, 즉 **정확히 1/24**로 돌아온다. 총 길이는 프레임별 길이를 불균일하게 만드는 방식으로 보존된다.

이 버그를 세 층에 대보면:

|층|왜 놓치는가|
|---|---|
|L1|AVFoundation을 쓰지 않는 순수 계산이다|
|L2|인코딩 **전** 픽셀 버퍼를 본다. 버그는 writer 안에서 발생한다|
|L3 (기존 3항목)|총 프레임 수·총 길이·첫/마지막 프레임 위치가 **전부 통과한다.** 틀리는 것은 중간 프레임의 경계뿐이다|

**세 층이 모두 초록불인 채로 S3가 무너지는, 현재까지 알려진 유일한 경로다.** 따라서 L3에 둘을 추가한다.

1. 내보낸 파일의 비디오 트랙 `naturalTimeScale`이 프로젝트 프레임레이트의 **정확한 분모**인가 (23.976이면 24000)
2. 프레임 duration이 **전부 동일한가.** 불균일하면 컨테이너가 양자화했다는 신호다

예방은 §5.5의 writer 타임스케일 명시 의무이고, 위 둘은 그것이 지켜졌는지의 검증이다.

**파생 결정 (M5에서 확정, D20):** 문서 `duration`이 프레임 경계에 맞지 않는 상태를 허용할 것인가.

- 허용한다면 → ceil로 늘어난 마지막 부분 프레임의 **내용이 정의되어야 한다.** 명시 없이 결정되면 §7.4-6 위반이다.
- 허용하지 않는다면 → "`duration`은 항상 `ticksPerFrame`의 배수"가 문서 불변식이 되고 위 문제 자체가 사라진다. 다만 소스 레이트 불일치 등에서 강제가 어렵다.

M5 이전에 결정할 필요는 없으나, **이 갈림길이 존재한다는 것을 M5 시작 시점에 알고 있어야 한다.**

L1과 L2는 M0/M1부터 존재해야 한다. M5에서 처음 작성하면 이미 늦다.

**L1의 매핑 함수는 GyeolCore에 둔다.** 시각↔프레임 인덱스 변환은 AVFoundation을 쓰지 않는 순수 계산이므로, Core에 두면 M0에서 8개 프레임레이트 전부에 대한 테스트를 지금 작성할 수 있고 프리뷰·내보내기 양쪽이 **같은 심볼을 import**하도록 강제된다. 이 함수가 두 벌 존재할 가능성 자체를 없애는 것이 요점이다.

`FrameRate`는 지원 8종만 담은 닫힌 열거형이며, NTSC 계열은 24000/1001·30000/1001·60000/1001의 **정확한 유리수**를 갖는다(소수 근사를 쓰지 않는다). 자유 입력 프레임레이트를 허용하지 않는 이유는 L1이 검증할 대상 집합이 정의되지 않기 때문이다.

### 4.2 S4 검증 방법

**측정 방법:**

```
model → Data₁ → model' → Data₂     에서     Data₁ == Data₂  (바이트 동일)
```

**임의의 `Data`에서 출발하는 바이트 동일성은 계약이 아니다.** 달성 불가능하기 때문이다 — §5.6이 git diff를 요구하는 이상 손편집은 정상 시나리오이고, 사람이 넣은 공백·키 순서는 재인코딩에서 정규화된다. 모델에서 출발해 인코더 출력끼리 비교하면 그 노이즈가 개입하지 않으면서 "디코드가 무언가 흘렸는가"는 그대로 잡힌다.

**성립 조건: 결정론적 인코더 설정(`.sortedKeys`).** 기본 `JSONEncoder()`는 키 순서를 결정론적으로 내지 않는다(부록 A-16, 실측 확인). 이 설정이 빠지면 S4 테스트가 무작위로 실패하고, 원인을 찾지 못한 채 "테스트가 불안정하다"며 기준을 완화하게 된다. 그 순간 S4는 무력해진다. §5.6.4의 인코더 단일화 규칙이 존재하는 이유다.

`Equatable` 기반 비교는 쓰지 않는다. 비교 구현에서 필드를 빠뜨리기 쉽고, 그러면 정작 잡으려던 직렬화 누락을 놓친다.

**게이트의 형태:** 모든 필드가 채워진 픽스처 문서(두 종류 트랙 복수, 미디어 클립과 생성기 클립, 미지 식별자 이펙트와 깊은 파라미터 트리, 자막, 마커, 비기본 스타일·설정)로 왕복 바이트 동일성을 검증한다. M0에서 통과했다.

- **파일 접근은 Core의 일이 아니다.** 지문 계산도 북마크 해석도 앱 레이어가 하고, Core는 앱이 준 값을 저장·직렬화만 한다(§5.6.5).

**편집 연산 제약 (M2에서 지킬 것)**

문서 모델(M0)이 값 타입 수준에서 강제하는 것과, 편집 레이어가 지켜야 하는 것은 다르다. 아래는 M2에서 편집 API를 설계하기 **전에** 알고 있어야 하는 제약이다.

- **최소 클립 길이는 1프레임이다.** 트림이 클립 자신의 시작을 넘어가면 길이가 0이나 음수가 되는데, 문서 모델은 그런 클립의 생성 자체를 거부한다(트랩). 편집 레이어가 클램프해야 한다.
- **교차 필드 불변식은 트랜잭션 경계에서 강제한다.** 클립이 참조하는 `MediaID`가 미디어 풀에 있어야 한다는 규칙이 대표적이다. 이건 개별 필드의 검증으로 닫을 수 없다 — 클립을 먼저 넣고 미디어를 채우든 그 반대든, 어느 한쪽 순서가 반드시 중간 상태에서 걸리기 때문이다. **M2의 편집 API가 이 강제 지점이 된다.** 문서 모델은 생성 시점과 디코드 시점에만 검사하며, 그 사이는 호출자의 책임이다.
- **유효하지 않은 중간 상태를 거칠 수 없다.** 검증 필드에 `didSet`이 걸려 있으므로 "잠깐 0으로 뒀다가 곧 고친다"는 패턴이 트랩된다. 계산을 먼저 끝내고 대입은 마지막에 한 번 한다.

**편집 API의 형태는 D26, 언두는 D27, 가상화는 D28에서 확정되었다(M2.0).** 아래는 그중 §5.2에 직접 걸리는 것들이다.

**드래그 중에 문서를 커밋하지 않는다. 조작이 두 종류로 갈린다.**

|종류|예|드래그 중|프리뷰|
|---|---|---|---|
|**구조를 바꾸는 것**|이동·트림·분할|임시 문서를 만들지 않는다. 뷰가 고스트만 그린다|갱신하지 않는다|
|**값만 바꾸는 것**|볼륨·페이드, 자막 스타일(M3), 스펙트럼·텍스트 파라미터(M4)|**커밋되지 않은 임시 문서 값**을 렌더에 넘긴다|실시간|

- **갈리는 근거는 겹침 금지(§5.6.6)다.** 클립을 끌고 가는 중간에는 겹치는 위치를 지나므로 **유효한 문서 값이 애초에 만들어지지 않는다.** 값 조작은 구조를 건드리지 않으므로 임시 문서가 항상 유효하다. 이 구분은 편의가 아니라 불변식이 나눠준 선이다.
- **값 조작에서도 §7.4-3은 유지된다.** 렌더는 여전히 (문서, 시각)의 순수 함수이며, 다만 그 문서가 아직 커밋되지 않은 값일 뿐이다. **프리뷰가 문서에 없는 값을 반영하는 형태는 금지한다** — 그 순간 S3가 무너진다.
- 커밋은 양쪽 다 드롭 시점 한 번이므로, D27의 "언두 coalescing 없음"이 성립한다.

**타임라인 렌더 제약 (M2에서 지킬 것)**

- **절대 타임라인 좌표를 GPU에 넘기지 않는다.** 뷰포트 시작을 원점으로 하는 상대 좌표를 CPU에서 계산해 넘긴다. 절대 좌표 계산은 `Int64` 틱과 `Double`로 CPU에서 한다.
    - 근거: Metal 정점 좌표는 float32이고 정수 정밀도 한계가 약 1,677만이다. 3시간을 프레임당 10px로 펼치면 약 389만 px이라 여유가 4배뿐이며, 더 확대하면 깨진다.
    - **깨지는 형태가 "줌을 많이 하면 클립 경계가 미세하게 떨린다"이다.** 원인을 부동소수 정밀도에서 찾을 사람이 없다. §10의 B-프레임 캐시 어긋남과 같은 종류의 조용한 실패다.
    - **좌표계는 나중에 바꾸면 렌더 코드 전체를 건드린다.** M2 시작 시점 결정 대상이다.
- **놀고 있을 때 그리지 않는다.** 온디맨드 렌더를 기본으로 하고, 재생 중에만 디스플레이 링크로 연속 갱신한다. 정점 버퍼 재생성은 뷰포트나 문서가 바뀔 때만 한다.
- **세로 가상화는 하지 않는다.** 트랙이 3+2 고정이므로 세로는 항상 5개다. 가상화는 시간 축에만 건다.
- **타임라인 썸네일은 프리뷰 경로가 아니다.** 별도로 뽑아 캐시하며 §4의 S3 검증 대상이 아니다. **단 시각 변환은 §5.6.1의 어댑터를 그대로 쓴다** — 면제받는 것은 무상태성이지 어댑터 경유가 아니다. 자체 시각 변환을 두면 §10의 "어댑터를 우회하는 `CMTime` 변환이 생김"이 발현한다.
- **파형·썸네일 타일이 없으면 빈 채로 그리고 도착하면 다음 프레임에 채운다.** 렌더가 IO를 기다리지 않는다.
- **최대 줌아웃에서는 자막 텍스트를 그리지 않는다.** 3,600개에 Core Text를 호출하게 되며, 그 크기에서는 어차피 읽을 수 없다. 사각형만 그린다.

**가시 범위 쿼리는 이진 탐색만으로 닫히지 않는다. 두 보정이 필요하다.**

1. **뷰포트 왼쪽 경계를 걸친 클립.** 시작 시각으로 이진 탐색하면 시작이 뷰포트 앞이고 끝이 안인 클립을 놓친다 — 화면 왼쪽을 채우고 있는 클립이 안 그려지는 형태다. **한 칸 뒤에서 시작하면 충분하며, 그 보장은 겹침 금지(§5.6.6)가 준다** — 경계를 걸치는 클립은 트랙당 최대 하나다.
2. **자막은 겹칠 수 있으므로 위 보장이 없다.** 얼마나 앞까지 봐야 하는지에 상한이 없고, 관행(3~10초)에 의존하면 긴 자막 하나가 조용히 사라진다. **쿼리가 `maxSubtitleDuration`을 인자로 받는다.** 이 값은 문서에 넣지 않고(파생 데이터) 쿼리가 매번 계산하지도 않는다(O(n)) — **앱이 계산해 보관하고 넘긴다.** D26의 클램프 분담과 같은 형태다.

### 5.4 자막 (WhisperKit)

**언어 정책 — 제한하지 않는다.**

Whisper 모델은 99개 이상의 언어를 지원하고 WhisperKit은 자동 언어 감지를 제공한다. 따라서 **언어를 제한하는 쪽이 오히려 추가 작업이다.** 엔진 레벨에서 아무것도 막지 않는다.

단, "동작한다"와 "품질을 보증한다"는 다르다. 2단계로 나눈다.

|티어|대상|의미|
|---|---|---|
|**T1 — 검증**|한국어, 일본어, 영어|개발자가 직접 듣고 품질을 판단할 수 있다. 회귀 테스트 대상. 전사 품질 이슈를 리포트로 받는다.|
|**T2 — 동작**|Whisper가 지원하는 나머지 전부|자동 감지로 동작한다. 전사 품질에 대한 보증은 하지 않는다(모델의 품질이지 우리 코드의 품질이 아니다). 렌더링·레이아웃 버그는 T1과 동일하게 받는다.|

T1의 기준은 "중요한 언어"가 아니라 **"개발자가 결과의 옳고 그름을 직접 판단할 수 있는 언어"**다. 평가할 수 없는 언어의 전사 정확도 이슈를 받으면 대응이 불가능하다. 중국어가 T1에 없는 이유가 이것이며, 사용자 수나 중요도와는 무관하다.

**언어를 코드에서 제한하지 않는 이유**

Whisper에는 영어 전용 모델(`*.en`)이 별도로 있고 이것만이 다국어 모델보다 작고 빠르다. 여기에 영어 외 언어가 하나라도 들어가는 순간 다국어 모델을 써야 하며, **다국어 모델은 3개 언어를 쓰든 99개를 쓰든 동일한 파일이다.** 즉 T1을 3개로 좁혀도 모델 크기·다운로드 용량·추론 속도에서 절약되는 것은 0이다. 오히려 목록 밖 언어를 거부하는 코드와 UI를 새로 만들어야 하므로 제한이 더 비싸다.

**레이아웃 검증 범위 — 라틴 + CJK**

전사 언어와 별개로, **자막 렌더링을 실제로 테스트하는 문자 체계는 라틴 + CJK로 한정한다.** 이건 실제로 비용을 아낀다.

|문자 체계|v1 취급|
|---|---|
|라틴, 한글, 가나, 한자|**검증 대상.** 테스트 체크리스트 포함.|
|아랍어, 히브리어 (RTL)|미검증. 깨지면 이슈로 받아 v2.|
|태국어, 크메르어, 라오어|미검증. 깨지면 이슈로 받아 v2.|
|데바나가리 등 인도계|미검증. 깨지면 이슈로 받아 v2.|

일본어를 검증하면 중국어 자막 조판은 사실상 함께 검증된다(가로쓰기 기준 금칙 처리·문자 폭·줄바꿈 규칙이 CJK 공통). 따라서 중국어는 **"깨지지 않는 것은 보장, 전사 정확도는 미보증"** 상태가 된다.

**기능**

- 오디오 트랙에서 자동 트랜스크립션 (언어 자동 감지 + 수동 지정)
- 결과를 편집 가능한 자막 세그먼트로 타임라인에 배치
- 텍스트 수정, 타이밍 조정, 분할/병합
- 자막 스타일: 폰트, 크기, 색, 외곽선, 위치 (프리셋 3~5개). **스타일은 문서 전체에 하나다** — §5.6.6.
- SRT 내보내기
- **모든 처리는 온디바이스. 편집·재생·전사·내보내기 중 네트워크 호출 0.** (모델 최초 다운로드 제외 — §11의 계약 3번)
- **모델은 런타임에 다운로드되며 앱 번들에 없다.** M1 번들 조사에서 확정되었다(부록 A-26). 귀결 셋:
    - **모델 크기는 앱 크기와 무관하다.** D4의 선택지는 순수하게 첫 실행 UX 문제이며, 사용자가 모델을 바꿀 수 있는 길도 열려 있다.
    - **저장 위치를 `~/Library/Caches/`에 두지 않는다.** OS가 비우면 600MB대를 다시 받는다. §5.6의 저장 범주 논리가 여기에도 적용되지만, 이것은 프로젝트 데이터가 아니라 앱 전역 리소스이므로 그 표에는 들어가지 않는다. D21에서 정한다.
    - **Hardened Runtime과의 상호작용은 M1에서 검증할 수 없다.** 모델이 번들에 없기 때문이며, M3로 이관되었다(§10, 부록 A-28).

**장시간 오디오 처리 요구사항**

3시간 오디오의 트랜스크립션은 실시간 대비 10~30배로 가정할 때 6~18분이 걸린다(추정치, §부록 A). 20분 영상에서는 스피너로 충분했던 것이 여기서는 성립하지 않는다.

- **부분 결과 실시간 반영** — 완료를 기다리지 않고 처리된 구간부터 타임라인에 자막이 나타난다.
- **중단 후 재개** — 청크 단위로 처리하고 진행분을 캐시에 즉시 기록한다. 크래시나 강제 종료 후 재시작 시 남은 구간만 처리한다(§4 S8).
- **백그라운드 처리** — 트랜스크립션 중에도 편집이 가능해야 한다.
- 진행률 및 취소.

**텍스트 레이아웃 제약 — 이건 v1에 지키지 않으면 나중에 전부 뜯어야 한다**

다국어를 받는 순간 진짜 비용은 전사가 아니라 **자막 줄바꿈과 렌더링**에서 발생한다.

|문자 체계|문제|
|---|---|
|아랍어, 히브리어|RTL. 텍스트 방향과 정렬이 반대.|
|태국어, 크메르어, 라오어|**띄어쓰기가 없다.** 문자 수로 자르면 단어 한가운데가 쪼개진다.|
|한국어, 중국어, 일본어|금칙 처리. 줄 첫머리에 올 수 없는 문자(`。`, `」`, `?` 등)가 있다.|
|데바나가리 등 인도계|자소 결합. 문자 개수 ≠ 시각적 길이.|

**규칙 1: 자막 줄바꿈을 직접 구현하지 않는다.**

- Whisper 세그먼트를 화면 폭에 맞출 때 `String`을 문자 수·인덱스로 자르는 코드를 쓰지 않는다.
- 줄바꿈 지점 계산은 Core Text(`CTTypesetter` / `CTFramesetter`)에 위임한다. ICU 기반 줄바꿈 규칙이 위 표의 대부분을 처리한다.
- 텍스트 길이를 다룰 때는 `String.count`가 아니라 Core Text가 계산한 실제 타이포그래피 폭을 쓴다.

**규칙 2: 폰트를 이름으로 하드코딩하지 않는다.**

한글·가나·한자를 한 자막 스타일로 다루면 폰트 폴백이 곧바로 문제가 된다. 라틴 폰트를 지정한 채 일본어가 들어오면 두부(tofu)가 뜬다.

- 폰트 폴백 체인 구성은 Core Text에 맡긴다. 특정 폰트 이름을 코드에 박지 않는다.
- 자막 스타일의 폰트 필드는 **선택적이며 nil이 기본값(시스템 폰트)**이다. SF 계열은 CJK 폴백이 자동으로 붙는다.
- **Core는 폰트 이름을 해석하거나 검증하지 않는다.** 존재하지 않는 폰트도 그대로 저장한다. 폴백은 Core Text의 일이다.
- 사용자가 임의 폰트를 고를 수 있게 하되, 해당 폰트에 없는 글리프는 폴백되도록 둔다. 폴백을 막고 두부를 보여주지 않는다.

이 두 규칙을 어긴 코드는 영어 테스트에서는 멀쩡히 동작하기 때문에 자동 테스트로 걸러지지 않는다. 코드 리뷰에서 막아야 한다.

### 5.6 프로젝트

- `.gyeol` 패키지 (NSFileWrapper 기반 디렉터리)
- 스키마 버전 필드 (§5.6.3)

**저장 범주는 셋이며, 어디에 두는지는 데이터의 성질이 결정한다.**

|범주|내용|위치|수명|
|---|---|---|---|
|**문서 본체**|사용자가 만든 것 전부. 이식 가능한 것만.|`.gyeol` 패키지 내 `document.json`|영구. 잃으면 복구 불가|
|**사이드카**|머신 로컬이지만 재계산으로는 못 얻는 것. **v1에서는 북마크 하나뿐이다.**|`.gyeol` 패키지 안, 문서 본체 밖|프로젝트와 동일|
|**캐시**|재계산 가능한 파생물 (파형·썸네일·FFT·트랜스크립트)|문서 밖 `~/Library/Caches/dev.gyeol.Gyeol/`, 콘텐츠 해시 키|OS가 임의로 비울 수 있음|

- 문서 본체는 JSON이며, 사람이 읽고 git diff 가능하다.
- **머신마다 값이 달라지는 데이터를 문서 본체에 두지 않는다.** 두면 내용을 고치지 않아도 다른 머신에서 열 때마다 파일이 바뀌고, git diff 요구사항이 형식적으로만 참이 된다. D18이 이 규칙의 첫 적용이다.
- **사이드카를 `Caches/`에 두지 않는 이유:** 그 디렉터리는 OS가 언제든 비운다. 재계산 가능한 것에는 문제가 없지만, 사이드카는 정의상 재계산이 아니라 **복구**를 거쳐야 얻어진다. 세부는 §5.6.8.
- **클립 소스는 `.media(참조)` 또는 `.generator(식별자, 파라미터)` 중 하나** — v1에서 **둘 다 구현한다**(§5.8). 생성기는 소스 에셋이 없는 클립이므로 `AVMutableComposition`의 에셋 기반 트랙 모델과 맞지 않는다. 커스텀 컴포지터에서 어떻게 다룰지가 v1 편입으로 늘어난 비용의 대부분이다.
- **자동 저장 및 크래시 복구** — 직접 구현하지 않는다. `NSDocument`의 `autosavesInPlace`와 버전 관리를 그대로 쓴다(D7). 영상 편집기에서 이것은 부가 기능이 아니라 생존 조건이며, M1~M2 동안 크래시는 반드시 발생한다.
    - **이것이 §5.6.7 검증 규칙의 근거다.** 자동 저장은 사용자가 저장을 누르지 않아도 디스크에 쓴다. 유효하지 않은 상태가 메모리에 존재할 수 있으면, 그것은 곧 열리지 않는 파일이 사용자 모르게 저장된다는 뜻이다.

#### 5.6.1 시간 표현

- 시간은 유리수. 프로젝트 타임스케일 **120000 고정.**
- `RationalTime`은 **임의 timescale을 다루는 범용 값 타입**이다. 오디오 샘플 시각(44100·48000 등)은 120000으로 정확히 표현되지 않으므로 타입 레벨에서 제한하지 않는다. 인코딩은 저장 표현을 그대로 보존하며 약분하지 않는다.
- **문서 경계의 시간은 별도 타입(`DocumentTime`)이며 항상 120000이다.**
    - 함수 헬퍼가 아니라 필드 타입으로 만든다. 그래야 변환을 잊는 것이 타입 수준에서 불가능하다.
    - **내부 표현은 120000 틱 `Int64` 하나로 정규화한다.** 호출자가 준 유리수 표현을 보존하지 않는다. `1/2`는 생성 시점에 60000틱이 된다.
        - **이래야 "항상 120000"이 문자 그대로 참이다.** 표현을 보존하면 실제 계약은 "120000으로 표현 **가능**하다"라는 약한 것이 되고, 조회할 때마다 변환이 필요해진다. 그 변환은 `RationalTime`의 범용 API를 거치므로 throwing이고, 도달 불가능한 실패 분기와 그것을 정당화하는 증명이 코드에 남는다. **정규화하면 셋이 함께 사라진다** — 증명할 것이 없어진다.
        - §5.6.1이 `RationalTime`에 요구하는 "약분하지 않는다"는 이 타입에 적용되지 않는다. 범용 타입과 정규화된 타입의 계약이 다르다.
        - 부수 효과: 3시간 프로젝트에서 자막 3,600개를 매 프레임 조회할 때(§5.2 가상화) 나눗셈 하나로 끝난다.
        - 유효하지 않은 상태가 **검사되는** 것이 아니라 **표현 불가능**해진다. §7.4-7이 지향하는 형태다.
    - **JSON에는 맨 정수(120000 틱 수)로 기록한다.** `"duration": 240000`이며 객체로 감싸지 않는다. 내부 표현이 이미 틱이므로 직렬화에 변환이 없다.
    - 근거: `DocumentTime`은 정의상 항상 120000인데 필드마다 timescale을 쓰면 같은 상수를 수천 번 저장하게 되고, 더 나쁘게는 그것이 **가변인 것처럼 보인다.** 손편집하는 사람이 timescale을 고쳐도 된다고 오해한다. `FixedPointScalar`가 `"volume": 10000`으로 1.0을 뜻하는 것과 같은 계약이다.
    - 실측: 이 변경으로 픽스처 문서가 6,751 → 4,775바이트(29% 감소), 자막 세그먼트 하나가 12줄 → 6줄이 되었다. 3시간 프로젝트 기준 4만 줄대에서 2만 줄대로 내려간다. §5.6의 "git diff 가능"이 형식적으로만 참이 되는 것을 막는다.
    - 디코딩은 맨 정수만 받는다. 분수와 Int64 범위 밖은 던지고, 구 객체 형태는 **무엇을 기대했는지 알려주는 메시지와 함께** 거부한다.
    - **생성 경로는 둘뿐이고, 손실이 있는 쪽은 이름에 드러난다.** §5.6.2가 `FixedPointScalar`에 정한 규칙과 같은 형태다 — 정확 변환(그리드 밖이면 nil)과 반올림 생성자(규칙을 인자로 받으며 기본값은 `.toNearestOrAwayFromZero`). **레이블 없는 생성자를 만들지 않는다.**
- **반올림이 필요한 변환은 이름에 반올림 사실이 드러나는 API 하나로만 제공한다.** 정확 변환이 조용히 반올림하도록 완화하는 경로는 없다. §4.1 L1이 잡으려는 버그가 정확히 이것이며, 프리뷰와 내보내기가 서로 다른 반올림을 쓰는 순간 S3가 무너진다.

**그 "하나"는 `CMTime` 경계 어댑터다.**

AVFoundation은 120000이 아닌 타임스케일로 시각을 준다. 프레임 경계 바로 아래 시각이 반올림으로 경계에 올라가거나 그 반대가 되면 프레임이 하나 밀린다. **§4.1 L1의 테스트는 이 경우를 잡지 못한다** — L1은 정확한 `DocumentTime`에서 출발하기 때문이다.

```
CMTime ──[어댑터 · projectRate를 받는다]──▶ DocumentTime ──[L1 매핑 · floor]──▶ 프레임 인덱스
       (여기서만 반올림.                    (항상 프레임          (나눗셈만 남는다)
        출력은 항상 프레임 경계 N·d)          경계 위)
```

**어댑터는 "가장 가까운 120000 틱"이 아니라 "가장 가까운 프레임 경계"로 스냅한다.** M1 구현에서 발견되어 v0.13에서 이 절이 교정되었다.

- 틱 반올림만 하면 버그가 그대로 남는다. 600 컨테이너가 23.976의 프레임 1 경계 5005를 5000으로 양자화했을 때, 틱 반올림은 5000을 **그대로 보존**하고 L1의 floor가 프레임 0을 내놓는다. 정확히 어댑터가 존재하는 이유인 그 버그다.
- **따라서 어댑터는 프레임레이트를 알아야 한다.** 순수한 타임스케일 변환이 아니다.
- 교정이 어댑터에 있어야 하는 이유는 "반올림은 어댑터에만, L1에 변형 금지" 규칙 자체다. L1에 반올림 변형을 두는 순간 §10의 "시각 반올림 API가 늘어남"이 발현한다.
- 잔차 상한 `60000/T`(아래)도 이 해석에서만 성립한다.

- **반올림은 경계에서 한 번만 일어난다.** 어댑터를 통과한 뒤로는 전부 정확한 계산이다.
- **L1 매핑을 이원화하지 않는다.** "정확한 시각용 floor"와 "부정확한 시각용 round" 두 벌을 두는 설계는 §10의 "시각 반올림 API가 늘어남"에 그대로 해당한다. 반올림은 어댑터의 일이고, L1은 어댑터의 출력만 받는다.
- **어댑터는 `GyeolCore`에 둔다** (D19). §5.6.5의 예외 규정을 함께 볼 것.

**반올림 API가 둘로 보이지만 층이 다르다. 경계를 지킨다.**

|API|아는 것|쓰는 곳|
|---|---|---|
|`DocumentTime`의 반올림 생성자|120000 틱만. **프레임 그리드를 모른다**|오디오 샘플 시각 등 프레임과 무관한 값|
|`CMTimeAdapter`의 그리드 스냅|`projectRate`를 받아 프레임 경계로|재생·스크럽·프리뷰·내보내기|

**둘의 차이는 반올림 여부가 아니라 프레임을 아는가이다.** §10이 경계하는 "반올림 API가 늘어남"에 걸리는 것처럼 보이지만 다른 층이며, 대신 **`DocumentTime`의 반올림 생성자를 프레임 정확도가 요구되는 경로에서 쓰지 않는다.** 오디오 경로에서 쓰던 것을 비디오 경로로 가져오는 순간 프리뷰와 내보내기가 다른 반올림을 쓰게 되고 S3가 무너진다. 이 경고는 해당 생성자의 주석에 직접 적는다.

**어댑터의 입력은 프레임 인덱스다.** 역방향(`DocumentTime → CMTime`)의 seek 함수는 시각이 아니라 프레임 인덱스를 받는다. §7.4-8이 프레임 인덱스를 권위로 정한 것의 API 표현이다.

**역방향 — seek 시각은 프레임 경계가 아니라 프레임 중앙으로 만든다.**

프레임 N을 보기 위해 `N × ticksPerFrame`으로 seek하면, AVFoundation이 이 시각을 에셋 타임스케일로 낮추며 아래로 반올림할 때 프레임 N-1이 나온다. `N × ticksPerFrame + ticksPerFrame / 2`로 seek하면 어느 방향으로 반올림되어도 프레임 N 안에 남는다.

- **이 오프셋은 `DocumentTime`으로 저장되지 않는다.** 어댑터 안에서 생겨 어댑터 안에서 죽는 값이다. 밖으로 새면 §7.4-7 위반이다.
- 오프셋을 붙이는 함수는 **이름에 그 사실이 드러나야 한다.** 조용한 오프셋은 §7.4-6이 금지하는 형태다.
- seek 허용 오차는 양방향 모두 0으로 지정한다.

**손실 보고 — residual을 삼키지 않는다.**

어댑터는 반올림으로 버린 양을 함께 보고한다. 정상적인 반올림 오차는 에셋 타임스케일 한 틱 수준이며 프레임 길이의 1%에 미치지 않는다. **그보다 크면 반올림이 아니라 다른 문제다** — 가변 프레임레이트이거나 프레임레이트 가정이 틀렸다. 조용히 스냅하면 그 신호를 잃는다.

- 임계는 **1/4 프레임 초과**로 잡는다. 정확히 1/4은 걸리지 않는다(strict `>`). 1/2 프레임(스냅이 실제로 틀려지는 지점)은 너무 늦다. 그 값에서는 이미 잘못된 프레임을 집고 있다.
    - **포함/미포함을 명시하는 이유:** 적어두지 않으면 나중에 `>=`로 "고치는" 변경이 들어온다. 1/4은 600 컨테이너 최악값(0.05프레임)의 5배라 이미 넉넉하고, 경계에서 정확히 1/4이 나오는 것은 인위적으로 구성해야 하는 상황이다.
- 재생 루프에서 임계 초과가 발생해도 재생이 죽어서는 안 된다. 호출자가 받아 진단으로 남기고 진행한다. **개발 빌드에서는 즉시 드러나야 한다.**

**M1 실측이 임계값을 뒷받침한다 (부록 A-23).** 일반화하면:

> 타임스케일 T로 낮출 때 잔차는 **`60000/T` 틱 이하**이고 **누적되지 않는다.**
> 1/4 프레임 임계를 넘으려면 **T < 2 × 프레임레이트**여야 한다.

- 600으로 낮출 때 최악 잔차는 100틱, 60fps 기준 0.05프레임으로 임계의 1/5이다. 임계값 변경은 불필요하다.
- 정확한 분모 타임스케일(24000·30000·60000·24·25·30·50·60)은 **전부 120000의 약수**이므로 모든 경계에서 왕복이 항등이다.
- `AVPlayer`의 현재 시각은 **나노초(10⁹) 타임스케일**로 온다. 120000보다 훨씬 촘촘해 잔차가 0.5틱 이하, 60fps 기준 0.00025프레임이다. **에셋 타임스케일로 말하는 API는 reader PTS, video output 표시 시각, `minFrameDuration`, `duration`뿐이며, 어댑터는 플레이어 시각이 미디어 타임스케일로 온다고 가정해서는 안 된다.**
- **그럼에도 round는 필요하다.** 나노초는 촘촘하지만 프레임 경계에 정확히 떨어지지 않는다(1001/30000초는 나노초로 정수가 아니다). 오차가 아무리 작아도 방향이 아래쪽이면 floor는 한 프레임을 밀어낸다. **크기가 아니라 부호의 문제다.**
- 따라서 임계가 실제로 걸릴 곳은 정상 경로가 아니라 **손상된 컨테이너와 가변 프레임레이트**다. 그쪽이 더 값진 용도다. 60fps에서 임계가 걸리려면 타임스케일이 120 미만이어야 하는데, 그런 파일이 온다면 경고할 값어치가 충분하다.

**가능한 곳에서는 반올림된 시각을 애초에 받지 않는다.**

|용도|경로|
|---|---|
|재생 중 표시 프레임 식별|`AVPlayerItemVideoOutput`이 픽셀 버퍼와 함께 돌려주는 표시 시각. 플레이어 현재 시각 폴링보다 정확하다|
|스크럽 / 정지 프레임|`AVAssetImageGenerator`, 허용 오차 양방향 0. 동기 `copyCGImage`는 deprecated이며 async API가 실제 시각을 함께 돌려준다|
|오프라인 분석 (파형·FFT·썸네일)|`AVAssetReader` 샘플 버퍼의 표시 타임스탬프. 에셋 원본 타임스케일이므로 반올림이 없다|

#### 5.6.2 스키마 규칙 — `Double`을 쓰지 않는다

문서 스키마에 부동소수 타입을 넣지 않는다.

|값 종류|표현|
|---|---|
|시간|`DocumentTime` (120000 틱 정수)|
|볼륨·불투명도·반응 감도 등 0~1 정규화 파라미터|고정소수점 정수, 스케일 10000|
|위치·크기|정규화 좌표를 같은 방식의 고정소수점|
|색|8비트 채널 정수 또는 hex 문자열|

**근거 (3개):**

1. **git diff 노이즈** — 슬라이더를 만졌다 되돌리면 `0.7000000000000001`이 남는다. §5.6이 diff 가능성을 요구하는 이상 이건 기능 저하다.
2. **언두 스냅샷 비교** — 문서 모델이 값 타입이고 언두가 스냅샷이므로(§7.4-4) `Equatable`을 쓰게 되는데, 부동소수의 `==`는 계산 경로에 따라 어긋난다. 슬라이더 드래그처럼 델타를 누적하는 조작에서 실제로 발생한다.
3. **일관성** — 시간은 유리수로 엄격하게 가면서 나머지를 부동소수로 두면, 나중에 "여기도 대충 해도 되지 않나"의 근거가 된다.

**왕복 실패는 근거가 아니다.** §4.2의 정의(인코더 출력끼리 비교)에서는 `Double`도 왕복한다. 이 점은 부록 A-15에 기록한다.

**스케일은 10000이다.** 1000은 부족하다 — 1080p 가로에서 1.92px, 4K에서 3.84px 단위가 되어 텍스트 오버레이를 1픽셀 단위로도 정렬하지 못한다. 10000이면 4K에서 0.384px로 서브픽셀까지 커버된다.

**고정소수점 타입 규칙**

정규화 파라미터는 raw 정수가 아니라 전용 값 타입(`FixedPointScalar`)으로 감싼다. 목적은 **변환을 잊은 것을 컴파일러가 잡게 하는 것**이다 — `Int`와 `Double`은 둘 다 숫자 타입이라 스케일이 적용된 값과 안 된 값을 타입 체커가 구별하지 못한다.

- **JSON에는 맨 정수로 기록한다.** `"volume": 7500`이며 객체로 감싸지 않는다.
- **0~10000으로 클램프하지 않는다.** 위치는 음수이거나 1을 넘을 수 있다(요소가 화면 밖으로 걸칠 때). 범위의 의미는 개별 파라미터의 것이지 타입의 것이 아니다.
- **`Double`로부터의 생성 경로는 둘뿐이고, 손실이 있는 쪽은 이름에 드러난다.** 반올림 생성자(기본 규칙 `.toNearestOrAwayFromZero`, 음수 대칭)와 정확 변환 생성자(불가능하면 nil). **레이블 없는 `Double` 생성자를 만들지 않는다.**
- **비유한 입력과 저장 범위 초과는 던진다.** 클램프하거나 트랩하지 않는다.
- **산술 연산자를 두지 않는다.** 더하기·곱하기는 UI 레이어가 `Double`로 한다. 저장 전용으로 유지하면 오버플로 논의 자체가 생기지 않는다.

**대가:** UI 경계에서 변환 함수를 거쳐야 하고, `"volume": 7500`은 `0.75`보다 손편집할 때 덜 친절하다. 스케일을 스키마 문서에 명시하는 것으로 완화하되, 없어지지는 않는다.

#### 5.6.3 미지 필드 보존과 스키마 버전

**이펙트·생성기 파라미터는 타입 태그된 값 트리(`GyeolValue`)로 저장한다.**

- 모르는 이펙트의 파라미터도 손실 없이 보존한다. §7.4-5(확장 지점을 미리 뚫어둔다)의 v1 내 실체는 이것 하나뿐이다.
- **알려진 이펙트도 같은 경로로 읽는다.** 경로가 갈라지면 "모르는 이펙트" 경로는 v1 내내 아무도 밟지 않아 버그가 발견되지 않는다.
- **`GyeolValue`에 부동소수 케이스를 두지 않는다.** 두면 §5.6.2 배제 규칙의 우회로가 된다. 유리수 케이스도 두지 않는다 — 필요한 플러그인은 객체로 중첩한다.
- `Double` 배제 덕분에 JSON number가 전부 정수이므로 `{"type":"int","value":64}` 같은 장황한 표현이 필요 없다. 실제 저장 형태는 `"params": { "barCount": 64, "sensitivity": 7500 }`이다.
- **디코딩은 엄격하다.** 소수부가 있는 수는 잘라내거나 반올림하지 않고 던진다. Int64 범위 밖도 던진다. 중첩된 값의 거부 오류가 상위 배열·객체 디코딩의 폴스루에 삼켜지지 않아야 한다 — 삼켜지면 진단이 "파일 어딘가가 잘못됐다"로 뭉개지고, 손편집 가능한 포맷에서 이건 치명적이다.
- 이펙트에 활성/우회 플래그를 두지 않는다. v1에는 그것을 토글할 UI가 없다.

**대가:** 알려진 이펙트도 컴파일러 타입 검증을 못 받는다. 키 오타와 타입 착오를 런타임이 잡는다. 그리고 v1의 이펙트는 우리가 만드는 둘뿐이고 플러그인 SDK는 v2(§6.3)이므로, **이 비용은 v1 내내 회수되지 않는 선불이다.**

**그 외 구조체의 미지 필드는 보존하지 않는다.**

- 모든 타입에 `extraFields`를 다는 것은 커스텀 `Codable` 보일러플레이트를 전면에 붙이고, §4.2가 검증하려는 대상을 흐린다.
- 대신 스키마 버전 `{ major, minor }`로 방어한다. 음수는 거부한다(§5.6.7의 3중 패턴). `0.0`은 정상 값이다.

**호환성 판정은 4종이며, Core는 판정만 반환한다.**

|판정|조건|앱의 대응|
|---|---|---|
|`compatible`|major 동일, 파일 minor ≤ 우리|그대로 연다|
|`readableWithLoss`|major 동일, 파일 minor > 우리|열되 "상위 버전에서 만든 파일이며 저장하면 일부 정보가 사라질 수 있다"를 경고|
|`migrationRequired`|파일 major < 우리|마이그레이션 후 열기. 마이그레이터는 문서 레이어에 있다|
|`unsupported`|파일 major > 우리|열기를 거부하고 앱 업데이트를 안내|

- **두 major 불일치를 하나로 합치지 않는다.** 합치면 문서 레이어가 "앱을 업데이트하세요"와 "파일을 변환할까요?"를 구별하려고 major를 **다시 직접 비교**하게 되고, 버전 비교 로직이 두 군데로 갈라진다.
- **Core는 불일치의 방향만 보고한다.** 마이그레이터가 존재하는지, 사용자에게 무엇을 보여줄지는 문서 레이어의 판단이다.
- **경고·안내 UI는 v1 범위다.** 없으면 스키마 버전 필드가 존재만 하고 하는 일이 없다.
- **남는 위험:** v1.1로 만든 파일을 v1.0에서 열고 저장하면 파라미터 밖 신규 필드는 사라진다. 경고할 뿐 막지 못한다. 의도적으로 감수한 트레이드오프다.

#### 5.6.4 인코더 단일화

- **문서 인코더는 단 한 곳에서 생성한다.** 설정: `.sortedKeys`, `.prettyPrinted`, `.withoutEscapingSlashes`, 그리고 바이너리는 명시적으로 base64.
    - `.sortedKeys` — 기본 `JSONEncoder()`는 키 순서를 결정론적으로 내지 않는다(부록 A-16, 실측 확인). 이것 없이는 §4 S4가 무작위로 실패한다.
    - `.prettyPrinted` / `.withoutEscapingSlashes` — 문서는 사람이 읽고 diff하는 것이 전제다. 이스케이프된 슬래시는 상대 경로 diff를 읽을 수 없게 만든다.
    - **base64를 기본값에 맡기지 않고 명시한다.** 문서 포맷은 계약이며, 조용히 바뀌는 기본값은 디스크에 있는 모든 북마크의 표현을 바꾼다.
- **프로덕션 코드에서 문서 데이터용 인코더·디코더를 따로 만들지 않는다.** 생성 지점이 둘 이상이면 설정이 갈라지고, **S4는 자기 자신의 불일치를 검출하지 못한다.**
- **단, 개별 값 타입의 단독 `Codable` 계약을 검증하는 테스트는 이 규칙의 범위 밖이다.** 그런 테스트가 문서 인코더를 쓰면 문서 포맷 설정이 바뀔 때 값 타입 테스트의 의미까지 흔들린다. 규칙의 대상은 프로덕션 경로다.
- 인코더 설정은 문서 레이어의 책임이다. 값 타입 안에 인코더 설정을 넣지 않는다.

#### 5.6.5 모듈 경계

- **GyeolCore는 `NSDocument`와 `FileWrapper`를 모르는 채로 둔다.** Core는 `Document ↔ Data`까지만 책임진다.
- **Core는 파일 IO를 하지 않는다.** 지문 계산, 북마크 생성·해석, 폰트 존재 확인 모두 앱 레이어의 일이다. Core는 앱이 준 값을 저장·직렬화만 한다.
    - **북마크는 v0.11부터 Core를 완전히 떠났다**(D18). 생성도 해석도 저장도 앱 레이어다. Core는 상대경로와 지문만 안다.
- **GyeolCore는 픽셀·줌 레벨·포인터 좌표를 모른다** (v0.18 신설, D26).
    - M2 이전에는 Core에 UI가 들어올 압력이 없어 적을 필요가 없었다. 편집과 타임라인이 붙는 순간 생긴다 — 스냅 임계("8픽셀 안이면 붙는다")를 Core에 넣고 싶어지고, 그 순간 Core가 줌 레벨을, 이어서 뷰 크기를 알아야 한다.
    - **경계는 이렇게 자른다: 후보 시각 계산은 Core, 임계 판단은 앱.** 클램프를 "범위 계산은 Core, 실행은 앱"으로 자른 것(D26)과 같은 형태다.
    - 이 조항이 없으면 Core의 테스트 가능성이 화면 크기에 의존하게 된다.
- 패키지 레이아웃(`.gyeol` 디렉터리 구성)과 자동 저장은 앱 껍데기의 어댑터가 맡는다. D7(NSDocument 채택)과 모순되지 않는다.
- 근거: Core가 순수해야 렌더 경로 순수성(§7.4-3)과 값 타입 원칙(§7.4-4)이 앱 없이 테스트 가능하다.

**CoreMedia는 예외다 (D19).**

`CMTime ↔ DocumentTime` 경계 어댑터(§5.6.1)는 `GyeolCore`에 둔다.

- **금지 대상은 파일 IO와 플랫폼 상태이지 값 타입이 아니다.** CoreMedia는 파일을 만지지 않고 상태를 갖지 않는다. Core의 테스트 가능성이 훼손되지 않는다.
- **근거는 §4.1이 L1 매핑을 Core에 둔 것과 동일하다** — 이 변환이 두 벌 존재하면 프리뷰 경로와 내보내기 경로가 서로 다른 반올림을 쓰게 되고, 그것이 S3가 무너지는 가장 유력한 형태다. 어댑터가 앱 레이어에 있으면 Core 테스트 밖에 놓이는데, S3의 실제 위험이 거기 있는 이상 받아들일 수 없다.
- **`AVFoundation`은 예외가 아니다.** 이 규정은 CoreMedia에만 적용되며 확장되지 않는다. `AVAsset`·`AVPlayer`·`AVMutableComposition`을 Core에 들이는 PR은 거절한다.

#### 5.6.6 문서 구조 — 정렬, 겹침, 자막의 위치

**정렬은 스키마 불변식이다.**

- 트랙 안의 클립, 자막 세그먼트, 마커는 모두 **시작 시각 오름차순으로 정렬된 상태로 저장**한다.
- 디코드에서 순서가 어긋나면 **던진다. 조용히 정렬하지 않는다.** 순서가 어긋난 파일은 편집 코드에 버그가 있다는 신호이며, 조용히 고치면 그 신호가 사라진다.
- 근거: §5.2의 뷰포트 가상화가 보이는 범위를 **이진 탐색**으로 찾는다. 3시간 프로젝트는 매 프레임 전체 순회를 감당할 수 없다. S7이 여기 걸린다.

**같은 트랙의 클립은 겹칠 수 없다.**

겹치면 렌더러가 어느 쪽을 그릴지 임의로 정해야 하고, 그것은 §7.4-3(렌더 경로는 순수 함수)과 정면으로 부딪힌다. 서로 다른 트랙 사이의 겹침은 정상이다(그것이 트랙의 존재 이유다).

**자막은 겹칠 수 있다.** 두 줄을 동시에 띄우는 것은 정상적인 자막 표현이다. 자막에는 정렬만 강제한다.

**자막은 클립이 아니다. 문서 최상위의 별도 컬렉션이다.**

근거 셋:

1. 3시간 프로젝트의 세그먼트는 1,000~3,600개다(부록 C). 클립으로 만들면 고정 비디오 트랙 3개가 자막으로 가득 차서 실제 영상 클립을 놓을 자리가 없다.
2. 편집 조작이 다르다. 클립은 트림·리플 삭제·스냅이고, 자막은 텍스트 수정·타이밍 조정·분할/병합이다. 한 타입으로 묶으면 모든 클립 연산이 "이게 자막이면?"을 분기해야 한다.
3. SRT 내보내기(§5.4)가 자막만 순회하면 된다. 클립이면 트랙을 훑으며 걸러내야 한다.

**텍스트 오버레이는 반대로 클립이다.** §5.8이 "분류만 다르다"고 한 것이 이것이다 — 자막과 **그리는 코드**는 공유하지만 **스키마상 위치**는 다르다. 텍스트 오버레이는 `.generator("text", params)`인 클립이다.

**자막 스타일은 문서에 하나다.**

세그먼트마다 두지 않는다. §5.4는 프리셋 3~5개를 요구할 뿐 세그먼트별 스타일 변경은 v1 범위에 없다. 세그먼트마다 두면 3,600개에 스타일이 복제되고, "이 자막만 빨갛게" 같은 UI 요구를 부르게 된다.

**미디어 풀은 UUID 문자열을 키로 하는 JSON 객체다.**

- `.sortedKeys` 하에서 같은 미디어 집합은 항상 하나의 정본 바이트 형태를 가지므로, 미디어를 추가하면 diff가 엔트리 하나로 국소화된다. 엔트리 배열은 정본 순서가 없어 논리적으로 같은 풀이 삽입 이력에 따라 다른 바이트가 된다.
- 주의: Swift는 비문자열 키 딕셔너리를 `[키, 값, 키, 값]` 평면 배열로 인코딩한다. 이 함정을 피하려면 키 타입이 문자열 키로 표현 가능해야 한다.
- **키 정규화로 인한 조용한 손실을 막는다.** 대소문자만 다른 두 UUID 키는 같은 식별자로 정규화되어 한 항목이 조용히 덮어써질 수 있다. 수동 디코드로 UUID가 아닌 키와 정규화 후 중복되는 키를 모두 거부한다.
- **알려진 한계:** 완전히 동일한 키가 두 번 나오는 JSON은 파서 단계에서 마지막 값만 남아 우리 코드에 보이지 않는다. 검출할 수 없다.
- **클립이 참조하는 `MediaID`가 풀에 없으면 디코드에서 거부한다.** 매달린 참조는 렌더 불가능하며, 로드 시점에 잡는 편이 나중의 nil 역참조보다 낫다.

**식별자는 UUID다.**

클립·트랙·마커·자막 세그먼트 전부 UUID를 가지며, **직렬화된 값을 유지한다**(재생성 금지). 언두 스냅샷에서 선택 상태를 복원하려면 필요하고, §4.2 왕복도 이것 없이는 성립하지 않는다.

배열 인덱스를 쓰지 않는 이유는 클립을 삽입하는 순간 모든 참조가 밀리기 때문이다. 자체 짧은 ID를 쓰지 않는 이유는 문서 안의 중복을 확인하는 코드가 새로 필요해지기 때문이다 — 새 실패 모드를 만들어 줄 길이를 줄이는 것은 남는 거래가 아니다.

UUID가 diff를 어지럽히지 않는다는 점도 확인했다. 자막 텍스트를 고치면 `text` 줄 하나만 바뀌고 `id` 줄은 그대로다.

**클립의 시간 표현**

```
Clip
  timelineStart: DocumentTime
  duration:      DocumentTime
  source:  .media(MediaSource)  |  .generator(식별자, 파라미터)
```

- **종료 시각을 저장하지 않는다.** 유도 가능하며, 저장된 복사본은 둘이 어긋날 자리가 된다.
- **`sourceStart`는 `Clip`이 아니라 `.media` 안에 있다.** 생성기는 소스 에셋이 없으므로 `Clip`에 두면 "생성기인데 sourceStart가 5초"라는 표현 불가능해야 할 상태가 표현 가능해진다.
- **연관값은 자기 자신을 검증하는 타입으로 감싼다.** Swift는 enum 케이스 생성을 가로챌 수 없지만, 연관값의 타입은 init·didSet을 가질 수 있다. 이 구조체는 직렬화에 노출되지 않으므로 와이어 포맷은 평면을 유지한다.

#### 5.6.7 검증 규칙

**검증은 값이 만들어지는 지점에 붙는다. 직렬화 경로에 붙이지 않는다.**

encode/decode는 경계이지 검증 장소가 아니다. 인코드 시점에 트랩하면 잘못된 값이 만들어진 순간과 발견되는 순간이 멀어지고, 자동 저장 중 크래시라는 최악의 실패 형태가 된다 — 스택 트레이스는 직렬화를 가리키는데 원인은 한참 전의 편집 조작이고, 사용자는 이유도 모른 채 작업을 잃는다.

디코드 검증만 예외인 이유는 **외부 파일은 만들어지는 지점이 우리 코드 밖**이기 때문이다. 그리고 외부 입력은 트랩이 아니라 **오류를 던져야** 한다.

**던진 오류의 진단은 사용자에게 도달해야 한다.**

문서 포맷은 손편집 가능하므로(§5.6) 디코드 실패는 사용자가 고칠 수 있는 종류의 실패다. 그런데 `DecodingError`의 기본 메시지는 "데이터를 읽을 수 없습니다" 수준이라, 어느 필드가 왜 틀렸는지를 버린다. **손실이 조용한 것이 아니라 손실의 원인이 조용한 형태**이며, §7.4-6의 취지에 걸린다. 다이얼로그는 뜨지만 정보가 없다.

값 타입의 디코더는 "37번째 자막의 start가 프레임 그리드를 벗어났다" 수준의 진단을 이미 만든다. 그 진단을 경계에서 버리지 않고 사용자에게 전달한다 — `CocoaError(.fileReadCorruptFile)`로 감싸며 coding path와 이유를 `NSLocalizedFailureReasonErrorKey`에 싣는다(M1.3 코드 리뷰 G7, 부록 A-33).

**검증 필드는 3중으로 막는다.**

|지점|수단|
|---|---|
|디코드|`throw` (외부 파일이므로 트랩 금지)|
|생성|`precondition`|
|대입|`didSet`의 `precondition`|

생성만 막으면 대입으로 우회된다. 값 타입의 필드는 나중에 대입될 수 있고, `autosavesInPlace`가 그것을 디스크에 쓴다.

**교차 필드 불변식은 이 패턴으로 닫을 수 없다.** 매달린 `MediaID`가 대표적이다 — 어느 필드에 `didSet`을 걸든 정당한 편집 순서 하나가 반드시 중간 상태에서 걸린다. 생성 시점과 디코드 시점에만 검사하고, 그 사이의 강제는 **M2의 편집 API가 트랜잭션 경계로서 담당한다**(§5.2).

**부작용:** `didSet` 검증이 있으면 유효하지 않은 중간 상태를 거칠 수 없다. 편집 코드는 계산을 먼저 끝내고 대입을 마지막에 한 번 해야 한다.

#### 5.6.8 사이드카 — 북마크

D18의 결과다. `.gyeol` 패키지 안, 문서 본체 밖에 북마크를 둔다.

**들어가는 것은 북마크뿐이다.**

`MediaID → 북마크 데이터` 매핑 하나가 전부다. **이 목록은 v1에서 늘어나지 않는다.** 늘어나는 순간 사이드카는 캐시가 아니게 되고, 아래의 모든 규정이 무효가 된다.

**불변식은 하나다: 사이드카가 통째로 사라져도 프로젝트는 정상 동작한다.**

사이드카가 비었을 때 실제로 일어나는 일은 다음 둘뿐이다.

1. 북마크 없음 → 상대경로로 찾음 → 사용자는 아무것도 눈치채지 못한다. **대부분 여기서 끝난다.**
2. 파일이 옮겨졌고 상대경로·지문 모두 실패 → 재연결 UI(S6)가 뜬다.

**최악의 결과가 "뜨지 않아도 될 재연결 UI가 떴다"이며, 이것은 데이터 손실이 아니라 편의 손실이다.** §7.4-6이 막으려는 종류가 아니다.

**§4.2 S4의 대상이 아니다.** 문서 데이터가 아니기 때문이며, 왕복 게이트를 두지 않는다. **대신 삭제 테스트를 둔다.**

|테스트|잡는 것|
|---|---|
|왕복 게이트 (두지 않음)|사이드카가 제대로 저장되는가|
|**삭제 테스트 (둔다)**|**사이드카에 의존이 새어들지 않았는가**|

후자가 실제 위험이다. 저장 실패는 아래의 자기 치유가 흡수하지만, **누군가 나중에 북마크 아닌 것을 사이드카에 넣는 것**은 왕복 게이트로 막지 못한다. "어차피 파일 있으니 이것도 같이"가 한 번 통과하면 사이드카는 캐시가 아니게 되고, 그때부터는 정말로 왕복 게이트가 필요해진다. 삭제 테스트는 그 순간 깨진다. **캐시라는 성질 자체를 지키는 테스트다.**

**자기 치유 — 단, 지문 검증이 앞선다.**

북마크 해석에 실패하고 상대경로로 파일을 찾아냈으면, **콘텐츠 지문이 일치하는 경우에만** 그 머신 기준 북마크를 새로 만들어 덮어쓴다. 이 갱신은 문서 본체를 건드리지 않는다.

- 지문 검증을 건너뛰면 안 되는 이유: 같은 위치의 **다른** 파일일 수 있다(재인코딩본, 동명의 다른 촬영본). 검증 없이 북마크를 갱신하면 잘못된 파일을 굳혀버리고, 그 뒤로는 재연결 UI조차 뜨지 않는다. §5.1의 3중 참조에서 세 번째 요소가 여기서 일한다.
- 이 규칙이 성립하면 북마크는 **쓸모 있는 동안은 항상 재생성 가능**하다. 재생성이 불가능한 상황에서는 원래 북마크도 어차피 해석에 실패했을 것이기 때문이다.

**해석에 성공했지만 stale인 경우도 같은 규칙을 따른다.**

M1.3 구현에서 드러난 공백이다. 북마크에는 실패 외에 **"성공 + stale"** 경로가 있다 — 사용자가 파일을 옮겼을 때 북마크가 추적에 성공하되 갱신이 필요하다고 알리는 경우이며, §5.1이 북마크를 쓰는 원래 이유가 정확히 이것이다. v0.14까지 §5.6.8은 실패 경로의 치유만 규정하고 있었다.

**지문 선행 갱신이라는 같은 규칙을 적용한다.** 추적에 성공했더라도 그 파일이 우리가 아는 그 파일인지는 별개 질문이며, 답은 지문만이 준다.

**지문이 없는 참조는 치유하지 않는다.**

지문은 선택적이므로(D24) 없는 참조가 존재할 수 있다. 이 경우 **해석은 하되 사이드카를 갱신하지 않는다.** 신원을 증명할 수단이 없는 상태에서 북마크를 굳히는 것은 위 문단이 막으려는 바로 그 상황을 만든다.

**치유를 즉시 디스크에 쓰지 않는다.**

사이드카 갱신을 저장하려면 문서를 변경됨으로 표시해야 하고, 그러면 **열기만 했는데 "편집됨"이 되며 자동 저장이 돈다.** 캐시 갱신이 문서 저장 트랜잭션을 발동시키는 구조이며, 이 절 전체가 의존하는 "사이드카는 순수 캐시"와 정면으로 어긋난다.

**치유는 메모리에만 반영하고, 사용자가 실제로 편집해서 저장할 때 함께 나간다.**

- 대가: 열고 닫기만 하면 치유가 남지 않아 다음에 또 폴백을 탄다.
- **그 대가는 지불할 만하다.** 폴백은 어차피 정상 동작이므로 손해는 해석이 한 번 더 느린 것뿐이고, 얻는 것은 문서를 건드리지 않는다는 성질 — 이 절이 지키려던 것 전부다.

**포맷은 바이너리 property list다. JSON이 아니다.**

- 북마크는 사람이 읽을 데이터가 아니므로 `.prettyPrinted`도 `.sortedKeys`도 의미가 없고, base64로 부풀릴 이유도 없다.
- 포맷이 다르면 §5.6.4의 문서 인코더 단일화를 **우회했다는 오해 자체가 생기지 않는다.** 같은 JSON이면 "이것도 문서 인코더를 써야 하나"라는 논의가 반복해서 돌아온다.

**저장 위치를 `~/Library/Caches/`로 옮기지 않는다.** §5.6의 범주 표 참조. 그 디렉터리는 OS가 임의로 비우며, 북마크의 수명은 프로젝트와 같아야 한다.

### 5.7 배포

- **GitHub Releases 직접 배포.** Mac App Store 사용하지 않음.
- **샌드박스 미적용.**
- **코드 서명 + 노터라이즈 필수.** (근거는 §7.3)
- 배포 형식: 서명·노터라이즈·스테이플된 `.dmg`
- **순서가 강제된다: 앱 서명 → 앱 노터라이즈 → 앱 스테이플 → dmg 생성 → dmg 서명 → dmg 노터라이즈 → dmg 스테이플.**
    - **dmg는 불변이므로 만든 뒤에는 안의 앱에 티켓을 붙일 수 없다.** 앱 스테이플을 건너뛰고 dmg만 스테이플하면 온라인 상태의 Gatekeeper 수락은 통과하지만, **dmg에서 꺼낸 앱 사본의 오프라인 첫 실행이 실패한다.**
    - 순서를 모르면 릴리스 당일에 처음부터 다시 굽게 된다. M1에서 실측한 재사용 체크리스트가 `docs/m1-notarization-roundtrip.md`에 있다.
- **엔타이틀먼트는 사용하지 않는다.** M1 왕복에서 빈 엔타이틀먼트로 서명·노터라이즈·실행이 모두 통과했다(부록 A-27). 나중에 무언가 추가된다면 **그것이 필요해진 이유가 반드시 있어야 한다.** "혹시 몰라서" 넣지 않는다.
- 업데이트: v1은 "새 버전이 있습니다" 알림 + 릴리스 페이지 링크까지만. 자동 다운로드·설치(Sparkle)는 v2.

### 5.8 생성기 — 오디오 스펙트럼 / 텍스트

§4 S0 때문에 v1에 편입되었다. 편입 근거와 대가는 §3, §9에 기록되어 있다.

**생성기 기반**

- 클립 소스가 `.generator`인 경우의 렌더 경로. 소스 에셋이 없으므로 커스텀 컴포지터에서 직접 처리한다.
- 생성기도 `render(document, time)` 순수 함수 원칙을 따른다. 프레임마다 계산하는 것이 아니라 사전 계산된 데이터를 조회한다.

**오디오 스펙트럼 — 범위를 여기서 고정한다**

이 기능은 방치하면 무한히 커진다. v1 범위는 다음이 전부다.

- **막대형(bar) 한 종류만.**
- 파라미터: 막대 개수, 색(단색 또는 2색 그라디언트), 위치·크기, 반응 감도
- 프리셋 3개
- FFT는 vDSP로 **사전 계산 후 캐시.** 파형 피크와 동일한 캐시 파이프라인을 재사용한다(문서 밖, 콘텐츠 해시 키).

**제외 — 요청이 와도 v1에서는 거절한다:** 원형·방사형, 파형(waveform)형, 파티클, 글로우·블룸, 반사, 주파수 대역 분할 커스터마이즈, 어택/릴리즈 커브 편집, 사용자 정의 셰이더.

**텍스트 오버레이**

- 정적 텍스트. 애니메이션 없음.
- **자막 렌더 경로를 재사용한다.** 자막을 위해 Core Text 렌더러와 스타일 시스템(폰트·크기·색·외곽선·위치)을 어차피 만들어야 하므로, 텍스트 오버레이는 "타이밍이 고정된 자막"과 그리는 코드가 동일하다. 추가 비용이 거의 없는 이유가 이것이다.
- 단 **스키마상 위치는 다르다** — 텍스트 오버레이는 클립이고 자막은 루트 컬렉션이다(§5.6.6).
- §5.4의 규칙 1(Core Text 줄바꿈 위임)과 규칙 2(폰트 폴백)가 그대로 적용된다.

|**문서 모델의 편집 연산**|M0의 값 타입에는 삽입·삭제·분할·트림 메서드를 두지 않는다. 편집 연산은 M2의 영역이며, 실제 조작이 무엇을 요구하는지 모르는 채로 API를 만들면 M2에서 다시 뜯게 된다.|
|**시각→프레임 매핑의 두 번째 구현**|"정확한 시각용"과 "부정확한 시각용"으로 L1 매핑을 나누지 않는다(§5.6.1). 반올림은 `CMTime` 경계 어댑터의 일이며, 그 뒤로는 정확한 값만 흐른다. 매핑을 나누는 것은 §10의 "시각 반올림 API가 늘어남"이 실제로 발현하는 형태다.|
|**사이드카에 북마크 외의 데이터**|§5.6.8. 사이드카는 캐시이며 그 성질이 §4.2 왕복 게이트를 면제받는 근거 전체다. 무엇이든 하나 더 들어가는 순간 면제가 무효가 되고, 그때는 왕복 게이트를 새로 만들어야 한다. **삭제 테스트가 이것을 막도록 설계되어 있다.**|
|**`ticks`에서 프레임 인덱스를 직접 계산하는 것**|`DocumentTime`이 틱으로 정규화되면서 `time.ticks / rate.ticksPerFrame`이 한 줄로 가능해졌다. **컴파일되고, 대부분의 경우 맞는 답이 나오므로 리뷰에서 걸리지 않는다.** 그러나 이것이 §4.1이 L1을 Core에 두어 없애려던 "매핑이 두 벌 존재하는" 상태의 시작이다. **`ticks`가 노출된 것은 정규화의 결과이지 직접 계산하라는 허가가 아니다.** 프레임 인덱스는 `FrameMapping`으로만 얻는다.|
|**소스 레이트와 프로젝트 레이트를 같은 파라미터로 받는 것**|M1은 단일 파일 재생이라 둘이 같은 값이지만, M2에서 30fps 프로젝트에 24fps 클립이 들어오면 그리드가 둘로 갈라진다 — **프로젝트 타임라인 그리드**(재생헤드·스크럽·프레임 이동)와 **소스 미디어 그리드**(소스에서 실제 프레임을 뽑을 때). 섞으면 §4.1이 서술한 그대로 S3가 무너진다. 파라미터 이름은 `projectRate`이며, 소스 그리드가 필요해지면 **별개의 이름으로 추가한다.** 이름이 `rate`이면 잘못된 호출부가 잘못돼 보이지 않는다.|
|**반환값 없는 `seek` 오버로드**|`AVPlayer.seek`에는 완료 핸들러 없는 fire-and-forget 오버로드가 있다. 이것은 seek가 후속 seek에 밀려 취소돼도 알려주지 않으므로, `playheadFrame`은 N인데 플레이어는 다른 곳에 있는 상태를 조용히 만든다 — **원칙 8이 막으려는 바로 그 불일치이며, M1.3 리뷰에서 F7로 한 번 고친 것이다.** 반환값(완료/취소) 있는 오버로드만 쓰고, 그 결과를 epoch로 판별한다. 반환값 없는 오버로드를 쓰는 코드는 F7을 다른 호출부에서 되살린다.|
|**드래그 중 문서를 커밋하는 것**|§5.2. 구조 조작은 드래그 중 유효한 문서 값이 존재하지 않고(겹침 금지), 커밋하면 언두가 드래그 한 번에 수십 단계로 쪼개진다. **커밋은 드롭 시점 한 번이다.** 이것이 D27의 "coalescing 없음"이 성립하는 전제이므로, 둘 중 하나만 무너져도 나머지가 함께 무너진다.|
|**선택 상태·재생헤드를 문서에 저장하는 것**|클립을 클릭만 해도 문서가 dirty가 되고 `autosavesInPlace`가 돈다. 선택은 언두 등록의 페이로드로, 재생헤드는 앱 상태로 둔다(D27). §5.6.6이 UUID 유지 근거로 든 "언두 스냅샷에서 선택 복원"은 문서에 넣으라는 뜻이 아니다.|
|**언두 coalescing 정책**|D27. 사용자 제스처 하나 = 트랜잭션 하나 = 언두 하나가 저절로 성립하므로 묶는 정책 자체를 만들지 않는다. 정책이 생기는 순간 "이 조작은 묶고 저 조작은 안 묶는다"는 표가 자라기 시작한다. **M3의 자막 텍스트 타이핑은 예외이며, `NSTextView`의 자체 언두라는 다른 층이다.**|

**노터라이즈는 선택이 아니다.**

macOS Catalina 이후 앱스토어 밖 소프트웨어도 기본적으로 노터라이즈를 요구한다. 더 중요한 것은 macOS Sequoia부터 **Control-클릭으로 Gatekeeper를 우회하는 방법이 제거되었다는 점**이다. 사용자는 시스템 설정 > 개인정보 보호 및 보안에 들어가 보안 정보를 검토하고 수동으로 허용해야 한다.

노터라이즈하지 않을 경우 사용자 경로:

1. 다운로드 → 더블클릭 → 차단
2. 우클릭 → 열기 (**더 이상 통하지 않음**)
3. 시스템 설정 → 개인정보 보호 및 보안 → 하단까지 스크롤
4. "그래도 열기" → 재확인

**§3의 타겟 사용자는 이 경로를 통과하지 않는다.** 개발자가 아니라 크리에이터다. 노터라이즈를 포기하면 제품을 만들 이유 자체가 약해진다.

**노터라이즈해도 첫 실행 다이얼로그는 남는다. 이 사실을 숨기지 않는다.**

M1 왕복에서 합성 quarantine으로 확인한 결과, 노터라이즈된 앱의 Gatekeeper 판정은 "허용되지만 **첫 실행 시 사용자 승인 필요**"였다(부록 A-27). 즉 실제 경로는 다음과 같다.

|경우|사용자 경로|
|---|---|
|노터라이즈 없음|차단 → 시스템 설정 → 스크롤 → "그래도 열기" → 재확인 (4단계, **대부분 이탈**)|
|**노터라이즈 있음**|**더블클릭 → 확인 다이얼로그 1회 → 열림**|

노터라이즈가 제거하는 것은 **차단**이지 다이얼로그가 아니다. README와 릴리스 노트에 "처음 열 때 확인 창이 한 번 뜹니다"를 적어 사용자가 놀라지 않게 한다. 이득을 과장하면 그 다이얼로그를 본 사용자가 오히려 의심한다.

따라서 **Apple Developer Program 연회비는 앱스토어를 쓰지 않아도 필수 비용이다.** "앱스토어 안 함"은 "연회비 안 냄"을 뜻하지 않는다. 필요한 것: Developer ID Application 인증서, 릴리스마다 `notarytool` 제출 → 티켓 수령 → staple.

### 7.4 아키텍처 원칙 (위반 시 PR 거절)

1. **엔진을 새로 만들지 않는다.** 코덱, 렌더 파이프라인, GPU 가속은 OS 프레임워크를 쓴다. 직접 짜는 건 UI와 편집 로직뿐이다.
2. **무거운 분석은 사전 계산 후 캐싱한다.** 렌더 시점 조회는 O(1)이어야 한다.
    - **캐시는 시각으로 인덱싱되므로 PTS 정렬이 선행한다.** 디코더가 돌려주는 순서를 그대로 믿지 않는다(§5.3). 어긋난 캐시는 크래시가 아니라 "조금 이상한 파형"으로 나타나므로 원인을 찾기 어렵다.
3. **렌더 경로는 상태를 갖지 않는다.** `render(document, time)` 순수 함수. §4의 S3가 이 원칙의 존재 이유다.
    - **적용 범위는 프리뷰·내보내기 경로다. 타임라인 뷰는 대상이 아니다**(v0.18 신설, D28). 이 원칙이 존재하는 이유가 전적으로 S3인데, **타임라인 뷰는 내보내기와 비교되는 대상이 아니다.** 파형 타일을 비동기로 채우다 한 프레임 늦게 그려도 깨지는 계약이 없다. 여기에 무상태를 요구하면 비용만 내고 얻는 것이 없다.
    - **면제의 근거는 "미디어 프레임을 렌더하지 않는다"이므로, 썸네일이 그 선을 넘는다.** 타임라인 썸네일은 별도 경로로 뽑아 캐시하며 S3 검증 대상이 아니되, **시각 변환은 §5.6.1의 어댑터를 반드시 경유한다**(§5.2).
    - **값 드래그 중 프리뷰는 이 원칙을 우회하지 않는다.** 커밋되지 않은 임시 **문서 값**을 넘기는 것이지, 렌더가 문서 밖 상태를 읽는 것이 아니다(§5.2).
4. **문서 모델은 값 타입이다.** 언두는 스냅샷, 렌더러 전달은 스레드 안전.
5. **확장 지점을 미리 뚫어둔다.** 구현은 나중에 해도, 데이터 구조는 지금 열어둔다.
6. **손실은 조용히 일어나지 않는다.** 반올림·절삭·범위 초과·데이터 소실은 이름에 드러나거나 던진다. §5.6.1과 §5.6.2가 이 원칙의 구체화다.
    - **소실이 금지되는 것은 사용자가 만든 데이터다.** 재생성 가능한 파생물은 대상이 아니다. **단, 무엇이 파생물인지 선언하는 곳은 재생성 경로를 함께 제시해야 한다.** 경로 없이 "캐시니까 괜찮다"고 말하는 것은 이 원칙의 우회다. §5.6.8이 이 단서를 쓰는 유일한 곳이며, 거기서 제시하는 경로는 지문 검증을 거친 자기 치유다.
7. **검증은 값이 만들어지는 지점에 붙는다.** 직렬화 경로에 검증을 넣지 않는다. 인코드 시점의 트랩은 원인과 발현 사이를 벌리고 자동 저장 중 크래시라는 최악의 형태가 된다. 디코드만 예외이며, 그것은 외부 입력이므로 트랩이 아니라 던진다. §5.6.7.
8. **시간의 권위는 프레임 인덱스에 있다.** `CMTime`은 언제나 파생물이다.
    - 역방향 변환은 이름에 반올림 사실이 드러나는 어댑터 **하나**로만 일어나며(§5.6.1), 그 어댑터를 통과한 뒤로는 전부 정확한 계산이다.
    - **재생 중 AVFoundation이 알려주는 시각으로 문서 상태를 갱신하지 않는다.** 정지 시점에 한 번만 프레임으로 확정하고, 그 인덱스로부터 다시 만든 시각으로 플레이어를 재동기화한다. 재생 중의 시각은 표시용 파생값이며 어디에도 저장되지 않는다.
    - 원칙 3이 렌더 경로의 무상태를 요구하는 것과 같은 이유이며, **시간 축에서의 표현이다.** 오차가 축적될 경로 자체를 없앤다.

    **핸드오프의 입력은 표시 중인 프레임의 PTS다. 벽시계 시각이 아니다.**

    플레이어가 보고하는 현재 시각은 벽시계라 거의 항상 프레임 중간을 가리킨다. 그러면 **화면에 보이는 프레임(floor)과 가장 가까운 경계(nearest)가 서로 다른 답을 낸다.** 절반의 확률로 확정된 인덱스가 화면과 어긋나고, 그 인덱스로 재동기화하면 **일시정지할 때마다 화면이 한 프레임 튄다.** 잔차 임계(§5.6.1)도 상시 초과된다 — 임계가 잘못된 것이 아니라 입력이 잘못되었다는 신호다.

    표시 중인 프레임의 PTS는 이미 그 프레임의 시작 시각이므로 floor와 nearest가 같은 답을 낸다. 남는 것은 컨테이너 양자화 오차뿐이고 그것은 유계다.

    **핸드오프는 재생이 멈추는 모든 경로에서 일어난다.**

    사용자의 일시정지 조작에 거는 것이 아니라 **정지 상태 전이 자체를 관찰한다.** 액션마다 핸드오프를 붙이는 방식은 새 경로가 생길 때마다 빠뜨리며, 실제로 M1에서 파일 끝 도달이 누락되어 앱이 재생 중이라고 믿는 상태가 남았다. M2는 정지 경로를 여럿 늘린다 — 클립 끝, 타임라인 끝, 재생 범위 끝, 편집으로 인한 중단.

    > **이 원칙은 한 문장이었는데 구멍이 둘이었다.** "무엇을 스냅하는가"와 "언제 스냅하는가"가 모두 비어 있었고, 둘 다 M1 구현에서만 드러났다. 설계 문장으로는 완결돼 보였다는 점을 기록해 둔다.

    **핸드오프는 원자적이다.**

    확정과 재동기화 사이에 다른 전송 명령이 끼어들 수 있는 구조는 이 원칙을 지키지 못한다. 진행 중인 핸드오프는 재생이 다시 시작되면 **무효이며 버려진다.**

    비동기 환경에서 이것은 자동으로 보장되지 않는다. M1 코드 리뷰에서 같은 실패로 끝나는 경로가 넷 발견되었다 — 큐에 대기 중인 핸드오프가 재생 재개 후 실행되는 경우, `await` 도중 재생이 시작되는 경우, 새 파일을 여는 동안 이전 파일 기준 핸드오프가 도는 경우, seek가 취소됐는데 그 결과를 버리는 경우. **넷 다 플레이어와 앱이 서로 다른 위치를 믿는 상태로 끝나며, 그것이 이 원칙이 막으려는 것 전부다.**

    각 경로에 개별 가드를 다는 방식으로는 닫히지 않는다. 다섯 번째 인터리빙을 놓친다. **전송 상태를 하나로 직렬화한다.**

    **확정할 수 없으면 확정하지 않는다.**

    프레임 증거(표시 중인 프레임의 PTS)를 얻지 못했을 때 벽시계 시각으로 대신하지 않는다. **마지막으로 확정된 인덱스가 권위를 유지한 채 재동기화하고, 확정하지 못했다는 사실을 보고한다.**

    벽시계 폴백은 위 세 조항을 우회하는 구멍이며, M1에서 실제로 프로세스를 죽였다: 어댑터가 프레임 N을 보기 위해 의도적으로 프레임 **중앙**으로 seek하는데(§5.6.1), 그 상태에서 폴백이 벽시계를 읽으면 경계로부터 정확히 0.5프레임 — 임계의 두 배 — 이 나온다. **우리가 만든 값이 우리 검증을 죽인 것이며**, debug에서는 크래시고 release에서는 조용히 잘못된 프레임이었다.

    > 원칙 8은 M1 동안 네 번 정제되었다. **무엇을 / 언제 / 원자적으로 / 없으면 하지 않음.** 최초 문장은 이 중 하나만 담고 있었다.

|~~**D26**~~|~~편집 API의 소재지와 형태~~|**결정됨: `GyeolCore`, 명시적 트랜잭션.** M2.0 설계 논의의 결과다.<br>**소재지가 Core인 이유는 검증 주체와 준수 주체가 같은 모듈에 있어야 하기 때문이다.** 편집 API가 지켜야 할 것(정렬·겹침 금지·최소 1프레임·매달린 `MediaID`)이 전부 Core의 값 타입이 강제하거나 디코드에서 거부하는 것들이다. 앱에 있으면 **계약의 양쪽을 동시에 보는 테스트를 쓸 수 없다.** D19가 어댑터에 적용한 논리와 같으나, 편집 연산은 `(Document, 인자) → Document` 순수 변환이라 CoreMedia조차 필요 없고 **§5.6.5의 예외 규정이 아예 불필요하다.**<br>**형태는 명시적 트랜잭션 + 단일 연산 편의 래퍼다.** 연산마다 완결하는 방식만으로는 닫히지 않는다 — "미디어를 풀에 추가하고 그것을 참조하는 클립을 넣는다"가 **어느 순서로도 중간에 유효하지 않은 상태를 지나기** 때문이며(§5.2), 합성 연산을 계속 늘리는 방향은 조합 폭발이다.<br>**§5.2의 "중간 상태 금지"와 충돌하지 않는다.** `didSet`이 잡는 것은 개별 필드(길이 0 등)이고 트랜잭션이 허용하는 것은 교차 필드(매달린 참조)다. 트랜잭션 안에서도 길이 0인 클립은 만들 수 없다.<br>**커밋 검증은 국소 검증이 기본이며, 디버그 빌드에서 전체 검증을 함께 돌려 대조한다.** 정렬·겹침·최소 길이·추가된 참조는 이웃 검사로 O(1)이고, O(n)이 필요한 것은 미디어 삭제 하나뿐인데 그것은 드래그 중에 일어나지 않는다. **국소 검증이 충분하다는 것은 증명이지 사실이 아니며, 대조 검사가 그 증명의 소비자다.**<br>**전체 검증 함수는 디코드 검증과 같은 함수여야 한다.** 두 벌이 되면 §5.6.4가 인코더에 대해 막은 형태가 되고, **대조는 자기 자신의 불일치를 검출하지 못한다.**<br>**클램프는 나누어 맡는다** — 범위 계산은 Core의 쿼리(`allowedTrimRange` 등), 실행은 앱, 연산 자체는 던진다. Core가 조용히 클램프하면 §7.4-6 위반이고, 정상 경로에서 던지게 하면 드래그마다 `try/catch`가 된다. 이 형태면 **한계를 아는 코드가 Core에 한 벌만 있고** 정상 경로에서 throw가 나지 않는다.<br>**Core의 쿼리는 상태를 갖지 않는다.** 인덱스 캐시를 들면 무효화 문제가 생기고 §7.4-3의 무상태성이 편집 경로에서 새어나간다. **이 조항은 D28의 이진 탐색 비용 측정에 의존한다** — 측정이 나쁘면 캐시를 조용히 넣지 않고 PRD 개정 사안으로 올린다.<br>**Core는 픽셀·줌 레벨·포인터 좌표를 모른다**(§5.6.5 신설 조항).|
|~~**D27**~~|~~언두의 소재와 입도~~|**결정됨: `NSUndoManager`, coalescing 없음, 페이로드는 (문서 값, 선택).**<br>**언두 단계 = 최상위 트랜잭션 하나. 묶는 정책을 만들지 않는다.** 보통 앱이 coalescing을 필요로 하는 이유는 드래그가 실시간으로 모델을 바꾸기 때문인데, **우리는 드래그 중 문서를 커밋할 수 없다**(§5.2, 겹침 금지와 `didSet`). 사용자 제스처 하나 = 트랜잭션 하나 = 언두 하나가 저절로 성립한다.<br>**참고할 선례가 없다는 것을 확인했다.** After Effects의 `beginUndoGroup`/`endUndoGroup`과 Photoshop의 `suspendHistory`는 실재하나 **둘 다 스크립트가 자기 작업을 묶는 표면**이며 대화형 드래그의 입도 문제를 풀지 않는다. 어도비 커뮤니티에도 실시간 슬라이더의 history를 묶는 방법에 대한 만족스러운 답이 없다. **"어도비가 익숙하니 따라간다"는 이 결정의 근거가 아니다.**<br>**`NSUndoManager`를 쓰는 이유는 D7의 연장이다.** `NSDocument`는 언두 매니저의 알림을 감시해 편집 상태를 자동으로 갱신하므로 `updateChangeCount:`를 직접 부를 일이 없다. 직접 스택을 만들면 저장 시점 추적을 손으로 재현해야 하고 `autosavesInPlace`와 어긋날 자리가 생긴다.<br>**`groupsByEvent`를 명시한다. 기본값에 맡기지 않는다.** 기본 동작은 "런루프 사이클 하나 = 언두 하나"인데 우리 계약은 "트랜잭션 하나 = 언두 하나"다. 지금은 사실상 일치하지만 일치하는 것과 계약인 것은 다르다. **§5.5의 writer 타임스케일, §5.6.4의 base64와 같은 형태의 규칙이며 세 번째 사례다.**<br>**언두 페이로드는 (문서 값, 편집 직전 선택)이다.** 선택을 문서에 넣을 수 없고(클릭만으로 dirty) 앱의 현재 상태로만 두면 언두 후 선택이 돌아오지 않는다 — 3시간 타임라인에서 되살아난 클립을 다시 찾아 클릭하게 된다. §5.6.6이 UUID 유지 근거로 든 "언두 스냅샷에서 선택 복원"이 여기서 완성된다. 문서를 그 시점 값으로 되돌리므로 **복원되는 선택 UUID가 존재하지 않는 경우가 구조적으로 없다.**<br>**선택 변경 자체는 언두 단계를 만들지 않는다.** 트랜잭션이 아니다.<br>**재생헤드는 페이로드에 넣지 않되 클램프한다.** 언두로 문서가 짧아지면 재생헤드가 타임라인 밖에 남을 수 있다.<br>**문서를 바꾸면서 언두에 등록하지 않는 코드를 금지한다.** 애플 문서가 "되돌릴 수 없는 변경이 있으면 언두 체인이 실제 문서 상태와 어긋난다"고 경고한다. **원칙으로 올리지 않는다** — 이 규칙은 `NSUndoManager`를 쓰는 한에서만 존재하며 D27을 뒤집으면 함께 사라진다. 결정에서 파생된 것은 §7.4에 올리지 않고, 대신 §10 리스크로 둔다.<br>**`levelsOfUndo = 100`.** 부록 C의 120MB 추정은 CoW가 전혀 먹지 않았을 때의 최악값이다. **M3에서 자막 대량 조작이 스택에 쌓일 때 재검토한다.**|

**M2의 하위 단계 (v0.18에서 배치)**

순서의 두 축은 **되돌리기 비싼 것을 앞으로**와 **소비자가 붙을 수 있는 것을 앞으로**다. 후자는 M1의 교훈에서 나왔다 — 설계 문장은 소비자가 붙기 전까지 검증되지 않는다.

**타임라인을 읽기 전용부터 만드는 이유.** 가상화는 M2에서 가장 되돌리기 비싼 구조인데 **편집 없이 완전히 검증된다.** 그리기·이진 탐색·줌/스크롤은 문서를 바꾸지 않는다. 편집을 같이 얹으면 60fps가 안 나올 때 원인이 가상화인지 편집 경로인지 갈라내기 어렵다.

**M2.2가 S7을 대리 측정한다.** §5.2·§10이 가상화를 M2 시작 시점에 확정하라고 요구하는 근거는 전부 S7(3시간·자막 2,000개 이상·60fps)인데, **자막은 M3에서 생기므로 §9 M2의 완료 조건만으로는 M3까지 아무도 검증하지 않는 구간이 남는다.** 자막 세그먼트는 문서 최상위 컬렉션이고 스키마가 M0에서 확정되었으므로, **WhisperKit 없이 손으로 만든 3,600개 픽스처로 M2.2에서 측정한다.** 이 공백은 v0.17까지 드러나 있지 않았다.

**deprecated API 이행(§10)을 M2.1에 붙인다.** §10은 "M2/M4 작업"으로만 지정했으나, M2.1이 문서 → 컴포지션 빌더를 처음 짓는 시점이므로 구 API로 쓰고 나중에 갈아타는 것보다 한 번이다. 더 중요한 것은 통과 조건 쪽이다 — §4.1이 요구하는 것은 "이행 후에도 L2가 비트 동일"인데, **이펙트도 편집도 없는 M2.1이 L2가 빨개졌을 때 원인이 하나뿐인 유일한 시점이다.** M4까지 미루면 생성기와 이펙트가 얹힌 뒤라 원인 분리가 어렵다.

**M2.3을 수평이 아니라 수직으로 자르는 이유.** "편집 API 전부 → UI 전부" 순서는 API가 완성될 때까지 화면이 안 바뀌는 무피드백 구간을 또 만들고(§10), 더 나쁘게는 **트랜잭션 경계라는 새 계약이 소비자 없이 전부 쓰여진다.** M1에서 원칙 8이 네 번 갈라진 그 상태다. 분할 하나가 M2의 새 계약을 전부 한 번씩 밟는다 — 편집 API의 형태, 트랜잭션 경계, 언두, 데이터 흐름(G2의 진짜 대체), **G1 전송 입구.** 분할이 첫 슬라이스인 이유는 트림이 D22를, 이동이 겹침 회피를 먼저 요구하는 데 비해 분할은 새 결정을 거의 부르지 않기 때문이다.

**언두는 별도 전송 경로를 만들지 않는다.** ⌘Z는 "문서 교체"의 한 형태이므로 G1을 제대로 닫으면 함께 닫힌다. M2.3의 수직 슬라이스가 G1의 두 입구를 모두 밟는 것이 이 때문이다.

**M2.1 픽스처에 30fps 프로젝트 + 24fps 클립을 넣는다.** §6.2의 "소스 레이트와 프로젝트 레이트를 같은 파라미터로 받지 않는다"는 아직 소비자가 없는 규칙인데, 픽스처 한 줄이면 M2.1에서 소비자가 생긴다. M2.4의 트림에서 처음 만나면 그때는 이미 파라미터 이름이 굳어 있다.

**임포트 UI의 마일스톤이 v0.17까지 배정되어 있지 않았다.** §5.1의 미디어 브라우저와 재연결 UI가 어느 마일스톤에도 없는데 D24가 "M2 임포트 UI에서 결정한다"고 M2를 전제하고 있었다. M2.5로 배정한다.

**빈 구간의 렌더 결과를 M2.1에서 정한다.** 클립이 없는 시각을 컴포지터가 무엇으로 채우는지가 PRD 어디에도 없다. M1은 단일 파일 재생이라 빈 구간이 존재하지 않았으나, 문서 재생에서는 트랙 시작 전·클립 사이·타임라인 끝 이후가 전부 빈 구간이다. **§7.4-3이 성립하려면 답이 정의되어 있어야 하고, 명시 없이 결정되면 §7.4-6 위반이다** — D20이 "ceil로 늘어난 마지막 부분 프레임의 내용"에 대해 지적하는 것과 같은 형태다.


**M1의 세 가지 단서**

1. **에셋 타임스케일 실측 — 완료.** 결과는 부록 A-23. **§5.6.1의 1/4 프레임 임계는 실측과 모순되지 않으므로 변경하지 않는다.** 최대 수확은 임계값이 아니라 `AVAssetWriter`의 기본 타임스케일 양자화였고, 그것이 §5.5와 §4.1 L3 두 곳을 바꿨다.
2. **L2 뼈대를 컴포지터 프로토타입과 같이 만든다.** §4.1이 "L1과 L2는 M0/M1부터 존재해야 한다"고 요구한다. 프로토타입이 무엇을 반환하는지가 L2의 계약을 결정하므로, **나중에 붙이면 프로토타입에 맞춰 계약이 휜다.** 이 시점의 L2는 `render(document, time)`의 출력 해시를 두 설정 경로에서 비교하는 최소 형태로 충분하다.
3. **노터라이즈 왕복 — 완료.** 다만 **의도했던 것을 검증하지 못했다.** WhisperKit이 정적 링크되어 중첩 바이너리가 없었으므로(부록 A-26), 이 왕복이 검증한 것은 D6이 겨냥한 중첩 바이너리 서명이 아니라 **파이프라인 전체**(인증서 → 서명 → 제출 → 스테이플 → Gatekeeper)다. 그것도 한 번 뚫어두면 릴리스마다 재사용되는 자산이므로 값이 있으나, **원래 목표를 달성했다고 기록하지 않는다.** 남은 리스크는 M3로 이관되었다(§10).

**눈으로 보이는 시점:** M0는 구조상 화면이 없다. 문서 모델은 앱 껍데기 아래층이며, 테스트가 유일한 감각기관이다. **처음 화면에 무언가 나오는 것은 M1이고, 편집기처럼 느껴지는 것은 M2, 실제로 쓸 수 있는 것은 M5다.** M0→M1이 피드백 없이 가장 긴 구간이며, 이것이 §10의 "1인 개발 지속성" 리스크가 실제로 발현하는 형태다. 기능이 부족해서가 아니라 재미가 없어서 멈춘다.

**피드백이 없다는 것의 다른 얼굴: 설계 문장은 소비자가 붙기 전까지 검증되지 않는다.**

M1에서 §7.4 원칙 8이 두 번 불완전한 것으로 드러났다. 한 문장이었는데 "무엇을 스냅하는가"와 "언제 스냅하는가"가 모두 비어 있었고, 문서 상태로는 완결돼 보였다. 첫 구현이 붙는 순간 둘 다 드러났다.

**PRD의 다른 조항도 같은 상태일 수 있다고 전제하는 편이 안전하다.** 특히 아직 소비자가 없는 것들 — §5.6.8의 사이드카(M1.3), §4.1의 L2(M1.4), §5.5의 writer 타임스케일(M5)이 후보다. 이것들이 M1의 원칙 8처럼 구멍을 드러내는 것은 실패가 아니라 정상이며, **그때 PRD를 고치는 것이 이 문서의 용법이다.**

**M4는 §5.8 편입으로 신설된 마일스톤이다.** v1 출시가 그만큼 늦어진다. §5.2 고정 트랙, §5.3 재생 속도 제거, §5.5 HEVC 내보내기 연기로 일부를 상쇄했으나 전부를 상쇄하지는 못한다. 이 비용은 §4 S0을 위해 의도적으로 지불한 것이며, "어차피 금방 된다"는 근거로 편입한 것이 아니다.

M5 이전에 §6의 항목이 추가되면 마일스톤 자체가 무효다.

## 11. 정체성 방어선

이 프로젝트가 무엇이 **아닌지**를 밖에도 명확히 한다.

- 슬로건에 "중국산 대체"를 쓰지 않는다. 동기로는 정당하지만 제품 얼굴로 내걸면 해외 기여자가 붙지 않고, 제품 수명이 정치 상황에 묶인다.
- 대신 사실로 말한다: **"영상은 이 맥을 떠나지 않는다. 자막까지 전부 로컬에서."**
- **주장의 방향이 중요하다.** §2가 지적한 CapCut의 문제는 네트워크를 쓴다는 것이 아니라 **클라우드 업로드를 전제한다**는 것이다. 우리가 부정하는 것은 **사용자 데이터의 유출**이지 네트워크 자체가 아니다.

**이건 마케팅 문구가 아니라 검증 가능한 기술적 주장이어야 한다.**

v0.11까지 이 자리에 "v1은 실제로 네트워크 코드를 갖지 않는다"라고 적혀 있었으나 **이는 사실이 아니며, M1 번들 조사(부록 A-26)로 확정되었다.** WhisperKit이 정적 링크되므로 모델 다운로드 코드는 **우리 실행 파일 안에** 들어온다. §5.4는 "(모델 최초 다운로드 제외)"로 예외를 두고 있었으므로 §11만 어긋나 있었고, **밖에 내거는 문장 쪽이 틀렸다는 점에서 더 나빴다.**

**v1이 실제로 지키는 계약은 셋이다.**

1. **사용자의 미디어와 프로젝트 데이터는 어떤 경우에도 전송되지 않는다.** 업로드 코드가 존재하지 않는다.
2. **자막 전사는 전부 온디바이스다.** 전사 API를 호출하지 않는다.
3. **네트워크가 열리는 곳은 둘뿐이다** — 모델 최초 다운로드(§5.4)와 업데이트 확인(§5.7). 둘 다 사용자가 인지하는 시점에 일어나며, **편집·재생·전사·내보내기 중에는 열리지 않는다.**

**계약 3번의 측정 방법이 §4의 S10이다.** 검증 가능하다고 선언하고 측정하지 않으면 v0.11에서 고친 문제가 형태만 바꿔 돌아온다.

**첫 실행 다운로드를 숨기지 않는다.** 600MB대 모델을 받는다는 사실을 README와 첫 실행 화면에 명시한다. 로컬 전용을 내걸면서 사용자가 예상하지 못한 다운로드가 발생하면, 그 순간 나머지 주장까지 함께 의심받는다. **첫 실행 시 Gatekeeper 확인 다이얼로그가 한 번 뜬다는 것도 같은 이유로 미리 알린다**(§7.3).

## 부록 A. 검증하지 못한 것

이 문서를 작성한 환경에는 Swift 툴체인도 Apple 프레임워크도 없다. 아래는 **이 문서를 쓴 환경에서 컴파일·실행으로 확인되지 않았다.** 일부 항목은 개발자의 실제 개발 환경에서 확인된 것이며, 그 경우 명시한다.

**처분 규칙 (v0.18 신설).** 미검증이라고 적고 넘어가는 것은 M1이 경고한 상태 그대로다 — 문서로는 완결돼 보이고 소비자가 붙을 때 갈라진다. **미검증 항목은 반드시 셋 중 하나의 처분을 받는다.**

|처분|의미|
|---|---|
|**검증**|지금 확인 가능하면 지금 한다. 웹 검색으로 닿는 API 존재·시그니처·deprecation이 여기 해당한다|
|**측정 예약**|**마일스톤과 "나쁘게 나오면 무엇을 하는가"를 함께 적는다.** 대응 없는 예약은 예약이 아니며, 그 순간 가장 쉬운 우회를 고르게 된다|
|**조건부 기록**|**어떤 결정이 이 미검증에 의존하는지 명시한다.** 의존이 적히지 않으면 나중에 측정이 나빠도 아무도 그 결정을 다시 보지 않는다|

세 번째가 특히 중요하다. §4.1의 L2가 "이행 후에도 비트 동일이면 통과"라고 조건을 명시해둔 것이 이 형태이며, 그 조항이 없었다면 API 이행 후 L2를 다시 볼 이유가 문서에 남지 않았을 것이다.

1. **프로젝트 타임스케일 120000** — **개발 환경에서 코드로 증명됨.** 지원 8종 프레임레이트 전부에서 프레임 길이가 120000의 정수 틱으로 떨어지는 것을 파라미터화 테스트로 확인했다(23.976→5005, 29.97→4004, 59.94→2002 등). 흔히 인용되는 600600은 NTSC 계열에서 깨진다.
    - **M1 실측 보강:** 8종의 정확한 분모 타임스케일(24000·30000·60000·24·25·30·50·60)이 **전부 120000의 약수**이므로, 이들 타임스케일과의 왕복은 모든 프레임 경계에서 항등이다. 손실이 생기는 것은 600처럼 약수가 아닌 타임스케일이 개입할 때뿐이다.
2. **`CMTime`의 `Codable` 준수 여부** — 확인하지 못했다. 자체 `RationalTime` 타입을 쓰기로 했으므로 실무상 영향은 없다.
3. **`AVVideoCompositing` 실시간 성능 — M1.4에서 실측됨.** 패스스루 컴포지터가 1080p에서 60fps 재생을 유지했다(62.9fps, 컴포지터 평균 17µs). 추정이 아니라 측정이다. **다만 이펙트 없는 패스스루의 수치이므로, 실제 합성 부하가 얹히는 M2/M4에서 재측정이 필요하다.** 부록 A-32.
4. **WhisperKit 한국어 성능 및 최신 API** — 실측 전이며, API 시그니처도 확인하지 않았다. 연동 코드 작성 시 최신 문서를 확인한다.
    - 웹 검색으로 확인된 것: WhisperKit v1.0.0(2026-05-01)에서 저장소가 `argmaxinc/WhisperKit`에서 `argmaxinc/argmax-oss-swift`로 이름이 바뀌었고, WhisperKit + SpeakerKit + TTSKit이 한 패키지로 묶였다. 라이선스는 MIT. 지원 하한은 macOS 14+ / iOS 17+로 우리 하한(macOS 26)보다 낮으므로 문제없다.
    - 자동 언어 감지와 수동 지정을 모두 지원한다는 기술이 있으나, 실제 API 형태는 확인하지 않았다.
5. **단어 단위 타임스탬프(word timestamps)의 오픈소스 제공 여부** — **정보가 충돌한다.** 한 출처는 WhisperKit의 기능으로 word timestamps를 명시하고, 다른 출처는 단어 단위 정렬이 오픈소스 범위 밖(Pro SDK)이라고 한다. 자막 타이밍 품질에 직결되는 사항이므로 M3 이전에 저장소에서 직접 확인해야 한다.
6. **Gatekeeper / 노터라이즈** — 웹 검색으로 확인했다. macOS Catalina 이후 앱스토어 밖 소프트웨어에 노터라이즈가 기본 요구되며, macOS Sequoia에서 Control-클릭 우회가 제거되었다는 것은 Apple 개발자 문서로 확인된 사실이다. 다만 **macOS 26/27에서 이 동작이 추가로 바뀌었는지는 확인하지 않았다.** 배포 준비 시점에 재확인한다.
7. **Apple Developer Program 연회비** — 금액을 확인하지 않았다. 지역·세금에 따라 다를 수 있다.
8. **샌드박스 미적용 시 TCC 동작** — 데스크탑·문서·다운로드 접근에 동의 프롬프트가 뜬다는 것은 알려진 동작이나, macOS 26에서의 구체적 UX는 확인하지 않았다.
9. **WhisperKit 실시간 배속(10~30x)** — 완전한 추정치다. 실제 값은 모델 크기, 칩, ANE 스케줄링에 따라 크게 달라진다. §부록 C의 트랜스크립션 소요 시간은 이 추정에 전적으로 의존하므로, M3 실측 전까지는 신뢰하지 말 것.
10. **§부록 C의 모든 수치** — 산술 계산은 맞지만 전제(세그먼트 평균 길이, 세그먼트당 바이트 수, 피크 해상도)는 전부 가정이다.
11. **Core Text가 태국어·크메르어 줄바꿈을 실제로 어디까지 처리하는지** — ICU 기반이므로 처리할 것으로 예상하지만 실측하지 않았다. M3 수동 체크리스트에서 확인한다.
12. **북마크 동작 세부** — macOS 버전에 따라 달라진 전례가 있다. 구현 시점에 재확인한다.
13. **macOS 26/27 관련 사실** — 2026년 7월 시점의 웹 검색으로 확인했다. macOS 27 Golden Gate는 2026년 6월 8일 발표, 퍼블릭 베타 7월 13일, 정식 출시 9월 예정이며 Intel Mac 지원이 종료됐다. 출시 일정은 변동 가능하다.
14. **§5의 모든 기능 목록** — 구현 난이도 추정치가 없다. M1~M4 진행 중 실제 소요가 크게 벗어나면 이 문서를 개정한다.
15. **`Double` 배제의 근거는 왕복 실패가 아니다** — 초기 논의에서 "`JSONEncoder`의 `Double` 출력이 왕복하지 않을 수 있다"를 배제 근거로 들었으나, §4.2의 정의에서는 `Double`도 왕복한다. **실제 근거는 §5.6.2의 세 가지(diff 노이즈·언두 비교·일관성)이며, 이 셋은 왕복 안정성과 무관하게 성립한다.** 나중에 "왕복은 되던데?"라는 이유로 이 결정을 뒤집으려 할 때 이 항목을 읽을 것.
16. **기본 `JSONEncoder()`의 키 순서 비결정성** — **개발 환경에서 실측 확인됨.** 동일 프로세스 내에서 같은 값을 두 번 인코딩할 때 키 순서가 달라지는 것을 테스트로 재현했다. §5.6.4의 근거다.
17. **`JSONDecoder`는 정수 표기를 구별하지 못한다** — **개발 환경에서 실측 확인됨.** 원시 토큰을 노출하지 않으므로 `1.0`, `1e2`, `1.5e1`처럼 **수학적 값이 정수인 것은 표기와 무관하게 통과**한다. 파서를 교체하지 않는 한 거부할 수 없다.
    - **문제되지 않는 이유:** 정보 손실이 있는 경우(`1.5`, Int64 범위 밖)는 확실히 던진다. 인코더 쪽에는 부동소수 케이스 자체가 없으므로 **쓰는 방향은 완전히 막혀 있다.** §4.2가 모델에서 출발하는 왕복이므로 손편집된 `1e2`가 `100`으로 저장되는 것은 계약 밖이다.
18. **정수 정밀도는 2^53을 넘어도 무손실** — **개발 환경에서 실측 확인됨.** `9007199254740993`(2^53+1), `Int64.max`, `Int64.min`이 정확히 디코딩된다. 순수 정수 토큰은 `Double` 경로를 타지 않는다.
19. **알려진 진단 부정확 (미수정)** — `GyeolValue`의 수 디코딩이 "Int64 실패 + Double 성공"으로 분수를 판정하므로, **Int64 범위를 넘는 정수도 "fractional"로 진단된다.** 값을 거부하는 동작은 옳으므로 안전성 문제는 없고, 오류 메시지만 어긋난다. 손편집 문서에서 사용자가 소수점을 찾는 헛수고를 하게 되므로, 해당 파일을 다음에 수정할 때 함께 고친다.
20. **완전 중복 JSON 키는 검출할 수 없다** — **개발 환경에서 확인됨.** 미디어 풀에서 대소문자만 다른 UUID 키는 수동 디코드로 거부하지만, **완전히 동일한 키가 두 번 나오는 JSON은 `JSONDecoder` 단계에서 마지막 값만 남아 우리 코드에 보이지 않는다.** 구조적 한계이며 우회 방법이 없다.
21. **M0 문서 모델 전체** — 개발 환경에서 구현·테스트 통과했다(**총 154 테스트**, M0 완료 시점 139에서 `CMTime` 어댑터·`DocumentTime` 정규화·`SnappedTime` 프레임 인덱스 테스트가 추가되었다). **이 문서를 작성한 환경에서 검증한 것이 아니므로**, 아래 동작 설명은 개발 환경의 테스트 결과를 옮긴 것이다.
    - 기반 값 타입: `RationalTime`(교차 timescale 정확 비교, `Int128` 교차 곱, Int32 timescale 축약 가드, 오버플로 경계, timescale 0 거부), `GyeolValue`(부동소수 없음, 맨 JSON, 분수·범위 초과 거부, 폴스루 삼킴 없음 — 깊이 5까지), `FixedPointScalar`(스케일 10000, 클램프 없음, 반올림 생성자 기본 away-from-zero, 산술 없음), `SchemaVersion`(판정 4종, 음수 3중 거부), `DocumentTime`(맨 정수 틱, 구 객체 형태 거부).
    - 문서 모델: `MediaReference` / `EffectInstance` / `MediaSource` / `ClipSource` / `Clip` / `FrameRate` / `ProjectSettings` / `Track` / `SubtitleStyle` / `SubtitleSegment` / `Marker` / `GyeolDocument`.
    - 검증 필드 전부가 디코드 throw + init precondition + didSet 3중으로 통일되어 있으며, trap 동작은 Swift Testing의 exit test로 검증했다(이 환경에서 동작 확인).
    - `GyeolCoding`: 문서 인코더 단일 생성 지점(§5.6.4).
    - §4 S4 게이트: 모든 필드가 채워진 픽스처로 바이트 동일 왕복 통과. 픽스처 크기 4,775바이트.
22. **§4.1 L1 매핑 — 개발 환경에서 완료.** `FrameMapping`으로 구현했고 8개 프레임레이트 전수 테스트를 통과했다. **v0.10에서 "M0 잔여"로 적혀 있던 항목이며 v0.11에서 해소되었다.**
    - **한계:** L1은 정확한 `DocumentTime`에서 출발하므로 **`CMTime` 경계에서 유입되는 오차를 잡지 못한다.** §5.6.1의 어댑터와 그 테스트가 이 구멍을 메우며, M1의 작업이다.
23. **에셋 타임스케일 실측 (M1) — 완료.** 보고서는 `docs/m1-asset-timescale-probe.md`, 도구는 `tools/TimescaleProbe`(일회용 CLI, GyeolCore 밖). 8레이트 × 2변형 = 16개 생성 클립을 프로브했다.
    - **최대 수확은 임계값 검증이 아니라 `AVAssetWriter`의 기본 타임스케일 양자화였다.** `mediaTimeScale`을 지정하지 않으면 트랙이 QuickTime 기본값 600으로 양자화된다. 정확한 1001/24000으로 써넣은 PTS가 25/600(= 정확히 1/24)으로 돌아왔고, 총 길이(3003/600)는 **프레임별 길이를 불균일하게 만드는 방식으로** 보존된다. `AVAssetWriterInput.mediaTimeScale` + movie 타임스케일을 명시하면 PTS가 정확히 유지된다(naturalTimeScale 24000, PTS 1001/24000). §5.5와 §4.1 L3가 이 발견의 결과다.
    - **1/4 프레임 임계는 실측과 모순되지 않는다.** 120000→600→120000 왕복은 NTSC에서 항등이 아니지만(5005→5000, 500500→500600) 잔차는 600틱의 절반 = 120000 기준 100틱으로 **유계이고 누적되지 않는다.** 최악 0.05프레임(60fps)으로 임계의 1/5 이하다. 일반화하면 잔차는 `60000/T` 틱 이하이며, 임계를 넘으려면 `T < 2 × 프레임레이트`여야 한다.
    - **`AVPlayer`의 현재 시각은 재생 중·정지 후 모두 나노초(10⁹) 타임스케일이다.** 에셋 타임스케일로 말하는 API는 reader PTS, video output 표시 시각, `minFrameDuration`, `duration`뿐이다.
    - **B-프레임:** `outputSettings: nil`인 reader는 샘플을 디코드 순서로 반환하므로 PTS가 비단조다. §5.3의 캐시 정렬 규칙이 여기서 나왔다.
    - **공백:** 실제 카메라·화면녹화 파일은 측정하지 못했다. TCC 차단이 아니라 해당 머신에 영상 파일이 없었다. **생성 파일은 우리가 만든 것이라 깨끗하고, 위 첫 항목이 보여주듯 진짜 변수는 컨테이너가 무엇을 하는가다.** 실제 촬영본이 생기면 `tools/TimescaleProbe`를 재실행한다. 그때까지 이 항목은 공백으로 남는다.
    - **어댑터 자체는 아직 구현되지 않았다.** 프레임 중앙 seek가 모든 코덱·컨테이너에서 의도대로 동작하는지도 미확인이다.

    - **L2 계약이 두 번 정밀화되었다(§4.1).** "버퍼를 해시한다"가 그대로는 성립하지 않았다 — 픽셀 포맷을 420v로 고정하고, `bytesPerRow` 패딩 때문에 이미지 바이트만 해싱하도록 했다. **둘 다 임계값을 도입하지 않는 방향이며**, 표현의 차이를 정규화해 내용 비교를 비트 동일로 유지했다. 360프레임 전부 비트 동일.
    - **생성기 자리 확인됨.** `AVVideoCompositionInstructionProtocol`의 `requiredSourceTrackIDs`를 비우면 소스 없는 프레임이 되고 `renderContext.newPixelBuffer()`로 새 캔버스를 받는다. §5.8의 생성기가 이 구조에 들어갈 자리가 있다. "불가능"이었으면 v1 범위를 다시 짜야 했다.
    - **`AVMutableVideoComposition`이 macOS 26에서 deprecated.** 프로토타입은 구 API를 썼다. §4.1·§10에 재검증 조건을 기록했다. **v0.19에서 SDK 실측으로 상황이 정밀해졌다 — 부록 A-35를 함께 볼 것.** 대체 타입이 아직 존재하지 않으며, 정작 이행 경로가 분명한 것은 픽셀 버퍼 타입 쪽이다.
    - **생성기 자리의 근거였던 `renderContext.newPixelBuffer()`가 `newReadOnlyPixelBuffer()`로 이행 대상이다**(A-35). 자리 자체는 유지되나 **이 확인 문장은 이행 시 재실행 대상이다.**
    - **async seek fire-and-forget 함정 소급 확인.** 반환값 없는 `seek` 오버로드가 F7을 되살릴 수 있어 `PlaybackController`가 반환값 있는 오버로드를 쓰는지 확인했다. §6.2에 규칙으로 추가했다.
    - `render(document, time)`은 순수하며 프레임 간 상태를 지니지 않는다(§7.4-3). 컴포지터 프로브도 이 계약 위에서 측정했다.
    - **GUI 없이 전수 검증되었다.** 이번 단계에는 GUI 필요 항목이 없었다.
33. **M1 마무리와 2차 코드 리뷰 — 완료, M1 봉인.**
    - **문서 라이프사이클 GUI 검증됨:** 문서 타입 등록, 열기·저장 패널, 자동 저장 왕복(⌘S 없이 디스크 반영 — `document.json` 수정 시각이 편집 후 저절로 갱신되는 것을 실측), Finder 더블클릭 열기, 상위 minor 경고 배너 화면 표시. 배너 문구는 "이 버전에서 저장하면 이 버전이 모르는 정보가 사라질 수 있습니다"로, §5.6.3의 요구를 전달한다.
    - **자동 저장 경로 원자성(부록 A-25 잔여 항목 해소):** in-place 자동 저장도 패키지 디렉터리 전체를 단일 rename으로 교체한다(두 번의 자동 저장 모두 디렉터리 inode 변경). **`document.json`만 손상되는 부분 저장은 이 경로에서도 불가능하다.** M2 편집을 얹기 전에 확인해야 했던 조건이며, 통과했다.
    - **2차 코드 리뷰에서 13건.** 1차와 달리 대부분이 M2 시점 항목이었고(§9 M2 진입 조건으로 이관), 즉시 처리한 것은 하나다.
    - **G7 — 디코드 진단 전달(처리됨).** 손상된 `document.json`이 `DecodingError`의 기본 메시지만 보여주고 GyeolCore의 필드·이유 진단을 버리고 있었다. `CocoaError(.fileReadCorruptFile)`로 감싸며 `NSLocalizedFailureReasonErrorKey`에 실어 전달하도록 고쳤고, §5.6.7에 규칙으로 반영했다. 마커 time을 1.5로 손편집한 문서에서 "fractional"과 필드 경로가 사유에 담기는 것을 테스트로 고정했다.
    - **G5 — 문서 해제 검증(측정, 변경 없음).** `makeWindowControllers()` → `close()`를 5회 반복하고 문서·창을 weak로 잡아 해제를 확인했다. 다섯 번 모두 해제되었다 — `NSDocument.close()`가 `document → windowController → window → DocumentView → document` 순환을 실제로 끊는다. **재실행 가능한 측정 테스트로 남겨** macOS 업데이트로 동작이 바뀌면 드러나게 했다. `DocumentView.file`을 weak로 바꾸는 것은 M2의 per-document 컨트롤러 구조가 정해진 뒤에 판단한다.
    - **이관된 리뷰 항목:** G1(epoch 확장), G2(수동 갱신 핵), G4(per-document 컨트롤러), G11(검증용 마커 버튼), G12(파일 기반 창과 문서 창 통합)는 §9 M2 진입 조건으로, G13(UTI 이중 진실)은 D25로 이관되었다.
    - **미해결로 남긴 것:** `DocumentView.file`을 weak로 바꿀지는 **M2의 per-document 컨트롤러 구조가 정해진 뒤에 판단한다**(G5). D27이 `NSUndoManager` 등록 대상의 수명을 건드리므로 M2.1에서 함께 본다 — 컨트롤러나 뷰가 해제될 때 등록된 언두 동작을 정리해야 한다는 규정이 여기 붙는다.
34. **M2.0 설계 논의 (v0.18) — 코드 없음, 결정과 처분만.**
    - **검증한 것 (웹 검색):** `AVVideoComposition.Configuration`의 **존재와 이행 방향**. `Mutable*` 계열이 `.Configuration`으로 이동한다는 것이 헤더 diff에서 확인된다. `NSUndoManager`의 `registerUndo(withTarget:handler:)`·`groupsByEvent`·`levelsOfUndo`·`removeAllActions(withTarget:)`의 존재와 의미. `NSDocument`가 언두 알림을 감시해 `updateChangeCount:`를 자동 호출한다는 것. `CVDisplayLink` 계열의 deprecation과 대체(`displayLink(target:selector:)` → `CADisplayLink`). `AVAssetImageGenerator`의 `image(at:)` async가 (이미지, 실제 시각) 튜플을 반환한다는 것과, `generateCGImagesAsynchronously`가 Swift 6에서 트랩된다는 보고. After Effects `beginUndoGroup`/`endUndoGroup`의 중첩 규칙과 Photoshop `suspendHistory`의 동작(**둘 다 스크립트 표면이며 대화형 드래그 입도를 풀지 않는다** — D27의 근거에서 "친숙성"을 제거한 이유).
    - **여전히 미검증 (조건부):** `AVVideoComposition.Configuration`의 **구체 형태.** 애플 문서 페이지가 JS 렌더링이라 내용을 얻지 못했다. **M2.1 착수 시 헤더로 확인한다.** `NSUndoManager` API의 macOS 26 변경 여부도 같다.
    - **측정 예약 (M2.2):** ①가시 범위 이진 탐색 비용 — **D26의 "쿼리는 무상태"가 여기 의존한다.** 넘으면 캐시를 조용히 넣지 않고 PRD 개정 사안으로 올린다. ②문서 전체 검증 1회 비용 — 편집 없이도 측정 가능하므로 소비자보다 먼저 당겼다. 넘으면 국소 검증이 선택이 아니라 필수가 된다. ③`GyeolDocument` 값 복사에서 CoW가 실제로 배열을 공유하는지 — **부록 C의 120MB 추정과 D27-2의 임시 문서 값 생성이 여기 의존한다.** ④썸네일 생성 처리량. ⑤파형 타일 크기와 밉맵 단계 수(구조만 고정, 숫자는 실측으로).
    - **측정 예약 (M2.3):** `NSUndoManager`와 `autosavesInPlace`의 상호작용. 언두로 저장 시점까지 되돌아갔을 때 자동 저장이 어떻게 행동하는지. **어긋나면 언두 채택(D27)이 아니라 저장 시점 추적을 재검토한다.**
    - **측정 예약 (M2.4):** 볼륨 드래그의 실시간 반영. **안 되면 §7.4-3을 깨는 방향이 아니라 실시간 미리듣기를 포기하는 방향으로 푼다.**
    - **일반 부동소수 사실에 의존하는 것:** Metal 정점 좌표 float32와 정수 정밀도 한계 2²⁴는 Metal 명세로 재확인하지 않았다. **다만 상대 좌표 결정은 이것이 틀려도 손해가 없는 방향이므로 그대로 간다.**
    - **이 논의에서 설계가 두 번 바뀌었고, 둘 다 다른 조항과 대보다가 드러났다.** (1) 값 드래그를 "앱 레이어 임시 값"으로 처리하려던 것이 §7.4-3과 정면으로 부딪혔다 — 커밋되지 않은 **문서 값**으로 고쳤다. (2) "매 프레임 전부 다시 그린다"가 놀고 있을 때도 60fps로 도는 형태였다 — 온디맨드로 고쳤다. **설계 문장은 다른 조항과 만나기 전까지도 검증되지 않는다.** M1은 이것을 구현과의 대면에서 배웠고, M2.0은 문서 내부의 대조에서도 같은 일이 일어남을 보여준다.

35. **macOS 26.5 SDK 실측 (M2.1 착수 전) — 완료. 결과가 예상과 달랐다.**
    - 환경: `MacOSX26.5.sdk`. 헤더 직접 확인이며 문서나 검색이 아니다.
    - **deprecation은 확정이다. 예정이 아니다.** `AVVideoComposition`(263행) / `AVVideoCompositionInstruction`(558행) / `AVVideoCompositionLayerInstruction`(654행) 셋 다 `macos(10.7, 26.0)` 형태로 **26.0에서 실제로 deprecated**되었고, 각각 `.Configuration`을 쓰라고 지시한다. `AVVideoCompositionCoreAnimationTool`만 버전 없는 `API_TO_BE_DEPRECATED`이며 `.init(configuration:)`을 권고한다.
    - **그런데 대체 타입이 이 SDK에 존재하지 않는다.** `AVVideoCompositionConfiguration` 등의 이름으로 헤더 전체를 재귀 검색해도 없고, `AVFoundation.apinotes`에도 없고, `.swiftinterface`·`.swiftmodule`도 없다. Headers의 `*Config*` 파일은 `AVCaptureExternalDisplayConfigurator.h`와 `AVSpatialVideoConfiguration.h` 둘뿐이다.
    - **이것이 "못 찾았다"가 아니라 "없다"인 근거:** 같은 apinotes에 `AVPlayerVideoOutputConfiguration` → SwiftName `AVPlayerVideoOutput.Configuration`이 있고, `AVVideoCompositionPerFrameHDRDisplayMetadataPolicy` → `AVVideoComposition.PerFrameHDRDisplayMetadataPolicy`도 있다. **중첩 이름을 만드는 메커니즘이 같은 SDK에서 다른 타입에는 적용되어 있다.** 메커니즘이 없어서 못 찾은 것이 아니다.
    - **`AVFCore.framework`는 SDK에 없다**(`AVFAudio`, `AVFoundation` 둘뿐). 따라서 `AVVideoComposition.h` 첫 줄의 `#if !__has_include(<AVFCore/AVVideoComposition.h>)`는 참이며, **우리가 읽은 본문이 실제로 컴파일되는 선언이다.** 조사 중 "이 헤더는 껍데기"라는 가설을 세웠으나 실측으로 폐기했다.
    - **가장 값진 결과는 컴포지팅 쪽이다. 프로토콜은 deprecated가 아니다.** `AVVideoCompositing`(114행)과 `AVVideoCompositionInstruction`(359행) 프로토콜 선언에 deprecation 속성이 없다. **M1.4가 `AVVideoCompositionInstructionProtocol`을 직접 구현한 커스텀 인스트럭션 구조(A-32)가 살아남는다.** M2.1의 작업량이 착수 전 예상보다 작다.
    - **대신 메서드의 픽셀 버퍼 타입이 이동한다**(전부 `API_TO_BE_DEPRECATED`): `newPixelBuffer()` → `newReadOnlyPixelBuffer()`(79행), `sourceFrame(byTrackID:)` → `sourceReadOnlyPixelBuffer(byTrackID:)`(266행), `sourceReadySampleBuffer` → `sourceReadySampleBuffer(byTrackID:)`(275행), `finish(withComposedVideoFrame:)`가 `CVReadOnlyPixelBuffer`를 받는 형태(289행). `AVCIImageFilteringParameters`(328행)도 함께.
    - **미확인:** 툴체인 쪽 Swift 오버레이 경로(`XcodeDefault.xctoolchain` 아래)는 검색하지 않았다. 26.5 이후 SDK에서 대체 타입이 나타나는지도 당연히 미확인이다. **다만 M2.1의 결정(현행 API + 빌더 격리)은 어느 쪽이든 바뀌지 않는다.**
    - **조사 방법에 대한 기록:** 첫 라운드는 셸 변수 `$SDK`가 빈 채로 실행되어 전부 무효였다. 에러 경로에 SDK 접두사가 없는 것으로 발견했다. **검색 결과가 "없음"일 때 그것이 진짜 없음인지 잘못 본 것인지 구별하는 데 비용이 든다** — 경로를 매번 계산하는 형태로 바꿔 재실행했다.

## 부록 C. 3시간 프로젝트 자원 추정

길이 상한을 20분에서 3시간으로 늘릴 때 무엇이 실제로 비싸지는지 계산한 결과. **전부 추정이며 실측하지 않았다.**

|항목|3시간 기준|판정|
|---|---|---|
|파형 캐시 (스테레오 48kHz, Int16 min/max, 512샘플/피크, 밉맵 포함)|약 16MB|문제없음. 문서 밖 캐시라 더욱.|
|언두 스냅샷 (자막 3,000개, 세그먼트당 400B, 100단계)|약 120MB|허용 범위. CoW로 자막을 건드리지 않는 편집은 비용 0.|
|AVComposition 세그먼트 수|길이와 무관|문제없음. 실제 컷 개수가 결정한다.|
|**자막 세그먼트 개수**|평균 10초 세그먼트 1,080개 ~ 평균 3초 세그먼트 3,600개|**비쌈.** §5.2 가상화의 근거.|
|**문서 JSON 줄 수**|자막 세그먼트당 6줄 기준 약 2만 줄|`DocumentTime` 맨 정수화 이전에는 4만 줄대였다(§5.6.1). 여전히 크지만 git diff가 성립하는 범위.|
|**트랜스크립션 소요**|실시간 10x 가정 18분 / 20x 가정 9분 / 30x 가정 6분|**비쌈.** §5.4 재개·부분결과의 근거.|
